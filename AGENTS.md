# Repository Guidelines

## Project Overview

This repository is a local, loopback-only Ground Console for SDR-DoA observation. It reads bounded Data Out resources, validates health and freshness, keeps native CSV/XML candidates separate, exposes publication-gate reasons, and renders the result in a React UI. The UI also provides a browser-only DoA simulation, local branding/configuration, renderer-only GPS/Compass choices, an optional MQTT monitor (sdr/v1 and RDF Node v2), and an embedded BrowSDR Receiver (route 7, see `CLAUDE.md`) that the Overview spectrum dock drives through a postMessage bridge. The monitor subscribes and never publishes on its own. The console has exactly one remote write: an admin-gated, explicitly confirmed sdr/v1 `cmd/config/patch` publish from the Kontrol panel on Overview. The edge agent decides whether to apply it and answers on `ack/config`.

This is not a production target tracker, RF range estimator, or general remote-control console. Map overlays are direction helpers, not transmitter locations or distance measurements. The Configuration page settings form is local or dry-run; the only real command is the Kontrol config patch. Read `initialize.md` first; active code and tests override historical documentation. There is no `README.md`.

## Architecture & Data Flow

```text
SDR-DoA Data Out
    -> tools/sdr_doa_collector.py
       bounded GET, schema parsing, redaction, freshness and consistency gates
    -> tools/ground_console.py
       loopback HTTP APIs and frontend/dist static serving
    -> frontend/src/App.tsx
       snapshot/config/MQTT state, local freshness, route and simulation orchestration
    -> page components
       Overview dashboard (map, HUD, node card, layers, Kontrol, polar + spectrum dock),
       health, diagnostics, configuration, monitor, simulation, receiver

Kontrol (Overview, admin) -> POST /api/mqtt/config-patch -> MqttMonitor.publish_config_patch
    -> sdr/v1/uav-01/cmd/config/patch (QoS 1, no retain, 60 s TTL) -> edge agent
    -> ack/config -> ConfigCommandTracker -> GET /api/mqtt/config-patch/<id> -> Kontrol
```

- The collector reads `/status.json`, `/settings.json`, `/DOA_value.html`, and `/doa.xml` only. It enforces host/path, timeout, response-size, numeric, freshness, and native-consistency rules. `collect(total_budget_s=...)` bounds one read; failed GETs are not retried, and the other resources are skipped when `status.json` is unreachable. A `NodeProgressTracker` reports a node whose status timestamp, uptime and DAQ frame index stop advancing (`NODE_CLOCK_STALLED` after 10 s; needs two reads). CSV/XML angles are compared only for same-frame pairs (`native_consistency.frame_relation`); adjacent or out-of-window pairs add `NATIVE_ANGLE_UNCHECKED`. DAQ sync failure or ADC overdrive make the snapshot `DEGRADED`. `overall_state` is checked in the order UNAVAILABLE, DEGRADED, INVALID, CONFLICT, STALE, INCOMPLETE, then UNVERIFIED/LIVE. Gate reasons added in the 2026-10 audit fixes: `NODE_CLOCK_STALLED`, `ADC_OVERDRIVE`, `COLLECTION_DEADLINE_EXCEEDED`, `CSV_VIEW_UNAVAILABLE`, `XML_VIEW_UNAVAILABLE`, `NATIVE_ANGLE_INVALID`, `ANGULAR_PEAK_ANGLE_MISMATCH`, `NATIVE_ANGLE_UNCHECKED`; every reason needs EN and ID labels in `lib/i18n.ts`. Display readiness and publication readiness are separate.
- `ground_console.py` is the Python boundary. API routes take precedence over static files, the server refuses non-loopback binds, and the active UI is the built React app. `--legacy-ui` selects the embedded previous interface. `/api/snapshot` is single-flight per base URL with a 4 s collection budget, so concurrent tabs share one collection and an unreachable Data Out reports UNAVAILABLE in about 4 s. Refresh intervals are 0 (manual), 1, 2, 5, 10 and 30 s, default 2 s, listed by `/api/capabilities`. An explicit `--base-url`, `--mqtt-host`, `--mqtt-port`, `--mqtt-transport` or `--mqtt-ws-path` overrides the saved `console.json` for that run. Without `paho-mqtt` the server still starts and the monitor reports ERROR. Capabilities are honest about the write path: `read_only: false`, `mqtt_publish: true`, `remote_post: false`, `config_apply: false`, `admin_default_password` (boolean only) and a `config_patch` block (`enabled`, `topic`, `qos`, `ttl_ms`, `ranges` from `sdr_doa_mqtt.CONFIG_RANGES`). The `/api/mqtt` monitor snapshot keeps `read_only: true, publish_enabled: false`, because the monitor never publishes on its own.
- The config-patch routes: `GET /api/mqtt/config-reported` (no admin; reported values, broker connection and the server-chosen `base_config_rev`, always 200), `POST /api/mqtt/config-patch` (body `{changes, base_config_rev, confirm: true}`, at most 4096 bytes; 202 with `command_id`), and `GET /api/mqtt/config-patch` / `GET /api/mqtt/config-patch/<command_id>` (command status, no admin; the bare path returns the latest command so a reload can resume). POST checks run in a fixed order and the first failure wins: Origin (403 `ORIGIN_REJECTED`), admin (401 `ADMIN_REQUIRED`), request shape, `confirm`, allowlist and ranges (400), monitor present, publish-capable and connected (409/503), base revision known and equal to the request (409 `CONFIG_REVISION_UNKNOWN` / `CONFIG_REVISION_STALE`), no other command in flight (409 `COMMAND_IN_FLIGHT`), then the publish (502 `MQTT_PUBLISH_FAILED`). Error bodies are `{ok: false, code, error, ...}`. `tools/config_command_tracker.py` keeps the last 32 commands on the server and derives each state from what the monitor saw for that id (PUBACK, the broker echo, the agent's ACK): `published`, `delivered`, `acknowledged`, then the final `acked`, `publish_failed` or `no_ack` (expiry plus 5 s). Correlation is server-side because the browser redacts payload keys ending in `id`. The base revision comes from the latest v1 `config_reported`, or a later live v1 `ack_config` (`applied`: its `config_rev`; `conflict`: `current_config_rev`), or else v1 `state`; RDF v2 `rev` is display only. `sdr_doa_lan_agent.py` subscribes to `cmd/config/patch` whenever `--publish` is on and, without `--enable-config`, answers every patch with a `rejected` ACK carrying `REMOTE_CONTROL_DISABLED`.
- `App.tsx` owns lifted application state and the language context. Automatic reads are a `setTimeout` chain; a tick or Refresh shares a read in flight instead of aborting it, and `displayFresh` depends only on data age and read failure, so Overview does not blank during a refresh. `/api/mqtt` has its own poll (2 s on Message Monitor and System Health, 5 s elsewhere). App also reads `/api/capabilities` once the config is loaded, owns the Overview panel state (`lib/overviewPanels.ts`), the draft that the spectrum dock hands to Kontrol (`lib/controlDraft.ts`), and the console's single Receiver bridge (`createReceiverBridge()` in a ref). The Receiver section mounts lazily, on the first `#/receiver` visit or the first Mulai/Dengar click in the Overview spectrum dock, never at console load (mounting auto-connects an authorized HackRF). After that it stays mounted and hidden, so RX, scans and recordings survive route changes until the console page reloads. `Shell.tsx` provides hash-based routes and one top bar on every route: a page-menu button (the popover lists the seven routes, with the theme toggle, the admin-gated-control chip and the shortcut hint in its footer; Escape, an outside click, Tab out or a navigation closes it), the brand mark, the route title and read age (not on Overview), the status strip (DATA, DOA, publication gate labelled Delivery/Publikasi, SNAPSHOT, MQTT, SIM), on Overview the panel toggles Lapisan | Polar | Spektrum | Kontrol, the refresh button, a refresh-interval select that saves through the same verified `updateConsoleConfig` path as Configuration, and EN|ID. Keyboard shortcuts are 1–7 pages and R refresh, also from inside the Receiver frame (`lib/shortcuts.ts`); a focused range slider counts as text entry. Pages, `TacticalMap` (MapLibre) and Plotly are lazy chunks loaded through `lazyWithRetry` and prefetched after load; `LoadErrorBoundary` limits a failed chunk or map crash to its area. `api.ts` uses same-origin requests with timeout, abort, response normalization, and config/branding read-back verification.
- `OverviewPage` is a full-map dashboard: the map fills the stage (`.ov-map`), the left column holds the `DoaReadout` HUD and the Lapisan panel (`LayersPanel`), the right column holds `NodeCard` and the Kontrol panel (`ControlPanel`), and the bottom dock holds `PolarDock` and `SpectrumDock` (all under `components/overview/` except the HUD). Which panels show, and whether the node card is collapsed, is a per-browser preference (`sdr-console-overview-panels-v1`; default Polar and Spektrum on, Lapisan and Kontrol off, node card collapsed). With both dock panels off the dock is not rendered. The page measures the floating panels with a ResizeObserver (`lib/mapInsets.ts`) and passes them to the map as padding, so the station is framed in the visible area. `OverviewPage` is memoized so the 500 ms freshness tick in `App.tsx` does not re-render the map or plot; every prop App passes to it must be stable (state, `useCallback` or a ref). One readiness predicate, `overviewDoaStatus()` in `lib/doaStatus.ts`, decides whether DoA is shown; its `shown` gates the HUD bearing, the polar curve and the map overlay (`doaReady`). Bearings are geographic: `geographicBearingForBin(bin, compassOffset)` in `lib/polar.ts` is (360 − θ₀ + offset) mod 360, and θ₀ stays visible as the array-frame value. The HUD shows bearing from north, age, θ₀, display peak, offset with its source, the held reason when DoA is hidden, and "Direction, not a transmitter location". The node card shows centre frequency and gain from `settings.fields`, the station position (the last live position is held during freshness gaps), and when expanded SNR, DAQ, ADC, DAQ frame, `en_remote_control` and the compass offset; its chip is `overall_state`. On Overview the publication gate shows only in the status strip. `TacticalMap` owns one MapLibre instance, OSM raster tiles (one host at a time: `tile.openstreetmap.de`, then `tile.openstreetmap.org` after repeated failures), station marker/popup, GeoJSON overlay layers (beam or density heat, lobe, bearing, −3 dB edges, range rings, guides), DOM text labels, a hover/tap readout, `OverlayLegend`, top-centre notices, and its own bottom-left controls (zoom in/out, centre on station, north up, OSM attribution link) in place of MapLibre's `NavigationControl`. Overlay settings are controlled by `OverviewPage`: the Lapisan panel has seven visibility toggles (including `edgesVisible` and `labelsVisible`), an `overlayOpacity` slider that scales every paint opacity, and an "Advanced"/"Lanjutan" disclosure that renders the existing `OverlayControls`. The overlay dB scale is Auto (from the vector) by default. Geometry rebuilds are debounced and only touch changed sources; palette, opacity, intensity, and blur are paint-only. MapLibre's worker is bundled by Vite and registered with `setWorkerUrl`; without it, GeoJSON layers never render. The style counts as ready on `styledata` because `load` waits for OSM tiles and may never fire offline. The canvas fallback draws on a non-tile error, without WebGL2, after WebGL context loss, or when the worker stalls. The camera is kept across route changes. `PolarPlot` renders with a partial Plotly bundle (`plotly.js/lib/core` + `lib/scatterpolar`, registered in `lib/plotlyPolar.ts`; a Vite plugin drops Plotly's MapLibre CSS) and preserves operator interaction while data updates. Polar mode draws θ₀ counter-clockwise like upstream KrakenSDR; Compass is north-up clockwise. `PolarDock` uses it without its own settings or mode bar and drives `head` and `range` as controlled props; both are part of the layout key and `uirevision`. Its Kompas|Polar switch and the "Adjust"/"Atur" column (Head Up; "Peak up"/"Puncak ke atas", which rotates θ₀ to the top via `peakUpHead()`; dB Auto/Manual; Reset) live in `lib/polarViewSettings.ts` (`sdr-doa-polar-view-v1`) and change only the plot and the HUD display peak. Its compass offset Data Out|Manual writes the Compass source config, which the map and the bearing use too.
- `SpectrumDock` draws a 2 MHz span around the Receiver's RX centre (512 bins, up to 10 fps) and drives the hidden Receiver frame through `lib/receiverBridge.ts`; the protocol is in `lib/receiverBridgeProtocol.ts` and on the frame side in the overlay's `console-bridge.ts` (see `CLAUDE.md`). Header controls: "Follow node frequency"/"Ikuti frekuensi node" (centre from Data Out `settings.fields.center_freq`, VFO from `doa_candidates.csv.frequency_hz_normalized`, fresh data only; `lib/nodeFrequency.ts`), the demodulation mode (NFM, WFM, AM, USB, LSB, DSB, CW, RAW), Listen/Dengar, "Send to Raspberry"/"Kirim ke Raspberry", Start/Stop (Mulai/Berhenti) and "Open full Receiver (7)". A click or arrow key on the trace or waterfall tunes the RX centre and the listen VFO (snapped to 1 kHz) and turns follow-node off. "Send to Raspberry" only opens Kontrol with a draft of `center_frequency_hz` and `vfo_frequency_hz`; it never posts. Spectrum frames go straight from the bridge to canvases, never into React state; only the bridge status goes through `useSyncExternalStore`.
- `ControlPanel` (Kontrol) has admin states `checking`, `locked`, `unlocked` and stages `edit`, `review`, `sending`, `done`. It reads `/api/admin/status` itself (the HttpOnly cookie is shared with Configuration), polls `/api/mqtt/config-reported` every 2 s while unlocked, posts only from the review step with `confirm: true` and the reviewed base revision, then polls the command status every 1 s until it is final. Fields, units (MHz, kHz, dB on screen; Hz and dB on the wire), fallback ranges and the hard-coded list of backend error codes are in `lib/configPatch.ts`.
- `doaGeometry.ts` generates geodesic bearing, lobe, guide, beam-sector, density-heat, range-ring, and −3 dB edge features, plus the −3 dB width and bearing/distance helpers. `overlayPalette.ts` holds the shared palette stops and MapLibre paint expressions. Signed dB normalization and projection distances are visual parameters, not physical RF conversions.
- `simulation.ts` creates a finite synthetic 360-bin snapshot with publication `BLOCKED` and no authority. `App.tsx` applies it only to Overview; health, diagnostics, runtime, and MQTT remain live, and so do the spectrum dock and Kontrol (follow-node ignores a synthetic snapshot).
- The staging telemetry path is separate: `sdr_doa_lan_agent.py` composes collector gates, safe MQTT contract messages, bounded latest-value queues, and the stdlib MQTT client. `sdr_doa_mqtt_monitor.py` (sdr/v1) and `rdf_node_mqtt_v2.py` (RDF Node v2) share one paho connection that subscribes: transport `tcp` or `websockets` (path `mqtt_ws_path`, default `/mqtt`), a random `groundconsole…` client id, no TLS or credentials. Its only publish is `MqttMonitor.publish_config_patch()`, called by the server for an admin-confirmed patch: QoS 1, `retain=False`, `MessageExpiryInterval` equal to the 60 s TTL, and only while connected with every SUBACK in, so paho never queues a command for replay after a reconnect. PUBACKs arrive through `on_publish`; `wait_for_publish` is never called under the monitor lock. The monitor also keeps a bounded record of v1 `config_reported`, `state`, `ack_config` and echoed `config_patch` messages for the config-patch path, outside the Message Monitor snapshot. Message Monitor shows per-kind counts, ages and STALE marks, and an RDF Node v2 panel that polls `GET /api/mqtt/rdf-node` every 2 s while the page is open.

## Key Directories

- `frontend/src/`: React/TypeScript application.
  - `components/`: shell, shared UI primitives, map, polar plot, admin unlock, and active renderers; `components/overview/` holds the Overview dashboard panels (node card, layers, Kontrol, polar dock, spectrum dock and canvas, panel toggles).
  - `pages/`: Overview, System Health, DoA Diagnostics, Configuration, Message Monitor, Simulation, and Receiver.
  - `lib/`: API-independent contracts and pure helpers for telemetry, DoA readiness, GPS/map, polar angles, geometry, overlay settings, MQTT monitor normalization, shortcuts, simulation, the Receiver bridge, the config-patch draft, spectrum axis math, and the Overview panel, polar-view and listen preferences.
- `frontend/scripts/build-receiver.mjs`: runs the Receiver builder for `npm run build:receiver` / `build:all`.
- `frontend/dist/`: generated production assets served by Python. Do not edit it as source.
- `tools/`: Python Ground Console, collector, edge/MQTT staging code, operational scripts, tests, and fixtures.
- `tools/fixtures/`: valid, stale, unhealthy, malformed, nonfinite, missing-status, conflict, partial, and peak-mismatch Data Out cases.
- `tools/browsdr_receiver_overlay/`, `vendor/BrowSDR` (submodule): Receiver sources; see `CLAUDE.md`.
- `deploy/`: example-only rollout/service material. Treat as plan, not an enabled deployment.

## Development Commands

Install and validate the frontend from `frontend/`:

```sh
cd frontend
npm ci --ignore-scripts --no-audit --no-fund
npm run check       # TypeScript build/typecheck, not lint
npm test            # Vitest run
npm run build       # tsc -b && vite build; empties and rewrites frontend/dist, including dist/receiver
npm run build:all   # npm run build, then tools/build_browsdr_receiver.py (needs vendor/BrowSDR)
npm run dev         # Vite development server on 127.0.0.1
npm run preview     # Vite preview on 127.0.0.1
```

Run the production UI through the Python server from the repository root:

```sh
.venv/bin/python tools/ground_console.py --bind 127.0.0.1 --port 8787
# legacy embedded UI, when specifically needed
.venv/bin/python tools/ground_console.py --legacy-ui --bind 127.0.0.1 --port 8787
```

The default URL is `http://127.0.0.1:8787/`. Vite alone does not provide the `/api` backend. Never expose the Ground Console or Vite server on a non-loopback address.

Useful backend checks:

```sh
PYTHONDONTWRITEBYTECODE=1 .venv/bin/python -m unittest discover -s tools -p 'test_*.py'
PYTHONDONTWRITEBYTECODE=1 .venv/bin/python -m unittest tools.test_ground_console_static
python3 tools/test_sdr_doa_collector.py
python3 tools/test_stage3.py
node --test tools/test_receiver_*.mjs   # Receiver overlay; needs vendor/BrowSDR and Node 22.13+
```

Most Python test files are standalone scripts with plain `assert` functions, so `unittest discover` does not execute every test. Run the named scripts when changing their modules. MQTT integration tests require a local staging broker on `127.0.0.1:18884`; use `tools/mqtt_stage4.conf` only for local staging. The config-patch tests (`tools/test_mqtt_config_patch.py`, `tools/test_config_patch_contract.py`) need no broker: they use a fake monitor and the fake paho client from `tools/test_sdr_doa_mqtt_monitor.py`. A synthetic publisher is available at `tools/synthetic_mqtt_publisher.py`.

## Code Conventions & Common Patterns

- TypeScript is strict. Normalize external values from `unknown`, then apply finite/range checks. Represent unavailable, stale, conflict, and error states explicitly instead of coercing bad data into valid-looking values.
- UI text lives in `lib/i18n.ts` with English and Indonesian dictionaries; read it through `useI18n()`. Add every key to both dictionaries (`i18n.test.ts` enforces key and placeholder parity). Status codes such as `STALE` or `BLOCKED` stay untranslated. The language choice is stored in `localStorage` under `sdr-console-lang`.
- Use pure helpers for contracts and transformations. Keep API validation in `api.ts`, telemetry readiness/gate logic in `lib/telemetry.ts`, GPS selection in `lib/map.ts`, angle conversion in `lib/polar.ts`, and GeoJSON math in `lib/doaGeometry.ts`.
- React state is lifted into `App.tsx` and passed through callback props. Effects must clean up timers, abort controllers, observers, MapLibre resources, Plotly instances, and listeners because the app mounts under `StrictMode`.
- Preserve latest-request-wins behavior and local freshness expiry. Do not recreate map/plot layout or camera state for ordinary data updates. Use `localStorage` only for local per-browser preferences (theme, language, overlay settings, GPS/Compass source choice, Overview panels and node-card collapse, polar view, listen mode, follow-node), with validation on restore and every access in try/catch.
- Components use `PascalCase`; functions, variables, and hooks use `camelCase`; constants use `UPPER_SNAKE_CASE`; Python modules/functions use `snake_case`; Python tests use `test_*` entry points.
- Python paths are intentionally bounded and defensive: allowlisted URLs, no redirects, finite timeouts, body limits, redaction, atomic local writes, and explicit loopback checks. MQTT payloads are schema-validated, size-bounded, and latest-value-wins per stream.
- Keep live, fixture, and synthetic data separate. Simulation must remain visibly labeled `SIMULATION` and must not affect health, diagnostics, MQTT, publication authority, or Raspberry state.
- Preserve the freshness gate, publication gate, redaction, CSP, timeout/abort handling, the monitor's rule that it never publishes on its own, and the dry-run boundary of the Configuration form. The one remote write is the Kontrol config patch (`POST /api/mqtt/config-patch` to `cmd/config/patch`). Keep all of its rules: loopback bind only; a port-exact same-origin loopback `Origin` header (no header or another origin gives 403 before the body is read); the admin cookie; `confirm: true` sent only after the UI review step; the server-side allowlist and `CONFIG_RANGES`; the reviewed `base_config_rev` must equal the server's; QoS 1, never retained, 60 s TTL (also as `MessageExpiryInterval`); at most one non-final command at a time; publish only while the monitor is connected with its subscriptions acknowledged; no MQTT in the browser and no MQTT credentials in the console. `POST /api/admin/login`, `/api/admin/logout`, `/api/console-config` and `/api/mqtt/connect` also require that same-origin loopback `Origin` (403 `ORIGIN_REJECTED`), because they control the admin session and the MQTT monitor that carries the patch; failed logins from other origins never reach the login throttle. The console itself never publishes the bearing. Do not add another remote write path, and do not expose secrets to `VITE_*` or browser state.
- Styles load in `main.tsx` as `styles.css`, then `console-design.css`, then `polar-layout.css`, then `overview-dashboard.css` (the `.ov-*` dashboard classes, `--ov-dock-h`, `--ov-gap`). Later files override earlier declarations. Dashboard touch targets are at least 44 px. At 1023 px or less the dashboard stacks in normal flow (map, HUD, Lapisan, node card, Kontrol, Polar, Spektrum) and the page scrolls; at 600 px or less it uses a 16 px side gutter. Check responsive and reduced-motion behavior when changing UI.

## Runtime/Tooling Preferences

- Use npm from `frontend/` with the committed lockfile. Project docs recommend Node 22.12+ within a supported Node 22 LTS; Vite/plugin engine ranges also accept newer supported Node versions. No root package manager, `.nvmrc`, or npm version is pinned.
- Use the project `.venv` for Python commands, Python 3.9 or newer (the console imports `zoneinfo` through the Receiver store). The Python tools are mostly standard-library code. `paho-mqtt==2.1.0` is needed for the MQTT monitor, synthetic publisher, and related tests; without it the console starts with the monitor in ERROR. On Windows, `tzdata` makes Receiver time filters follow the browser time zone.
- There is no Python dependency manifest, formatter, linter, CI workflow, Docker/Compose setup, or coverage configuration. `npm run check` is the defined static check; there is no `npm run lint`.
- Build `frontend/dist` with `npm run build:all` before full static-serving QA. The static regression suite skips build-dependent checks when `frontend/dist/index.html` is absent, and fails its Receiver checks when `frontend/dist` exists and `vendor/BrowSDR` is checked out but `frontend/dist/receiver` is missing.
- Keep credentials in the process environment or ignored root `.env`. `SDR_DOA_ADMIN_PASSWORD` is Python-only; never rename it to a `VITE_` variable or embed it in the frontend bundle. The process environment wins over `.env`. When the variable is absent from both, the default password `123456` applies: the server prints a startup warning, capabilities report `admin_default_password: true` (never the password), and Kontrol shows a warning. An explicitly empty value (`SDR_DOA_ADMIN_PASSWORD=`) disables admin login (503 `ADMIN_DISABLED`). A `.env` that exists but cannot be read or decoded also disables login instead of falling back to the default. After 5 failed logins within 60 s, every login, the correct one included, gets 429 `ADMIN_LOGIN_THROTTLED` for 30 s (counted for the whole server). The admin session is an HttpOnly, SameSite=Strict cookie with a 30 min TTL; it unlocks branding and Kontrol. Password changes need a console restart.
- Local console defaults are loopback bind `127.0.0.1`, port `8787`, Data Out `http://doasdr.local:8081` (allowed hosts `doasdr.local`, `192.168.100.100`, `127.0.0.1`, `localhost`, port 8081), and MQTT `10.90.0.1:9001` over WebSocket. The MQTT host may be any IPv4/IPv6 literal or `localhost` (no DNS names); the console opens an outbound MQTT connection there (it subscribes, and publishes only an admin-confirmed config patch) while its own HTTP bind stays loopback. A Kontrol send works only through a broker that accepts this anonymous, non-TLS client and lets it publish to `sdr/v1/uav-01/cmd/config/patch`. Staging broker files are not production security configurations.
