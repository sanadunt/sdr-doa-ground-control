# Repository Guidelines

## Project Overview

This repository is a local, loopback-only Ground Console for SDR-DoA observation. It reads bounded Data Out resources, validates health and freshness, keeps native CSV/XML candidates separate, exposes publication-gate reasons, and renders the result in a React UI. The UI also provides a browser-only DoA simulation, local branding/configuration, renderer-only GPS/Compass choices, an optional MQTT monitor (sdr/v1 and RDF Node v2), and an embedded BrowSDR Receiver (route 2, see `CLAUDE.md`) that the Dashboard spectrum dock drives through a postMessage bridge. The Overview route (id `overview`, `OverviewPage`, `ov-*` classes) is labelled Dashboard in the UI and lives at `#/dashboard`; `#/overview` still opens it. The UI calls the Raspberry node RDF-SDR and the HackRF receiver RadioSpectrum (labels only; identifiers, API fields, MQTT topics and the WebUSB filters keep their names, and the browser's own USB chooser still shows the USB product name). The monitor subscribes and never publishes on its own. The console has exactly one remote write: an admin-gated, explicitly confirmed sdr/v1 `cmd/config/patch` publish from the Kontrol panel on the Dashboard. The edge agent decides whether to apply it and answers on `ack/config`. Everything the operator saves (connection, MQTT, refresh interval, branding, the admin password in an env file, Receiver records and their Records retention setting, and the browser UI preferences through `/api/preferences`) lives in files on the console host, so it survives another browser, a cleared cache and a container rebuild. Linux packaging ships the console as a Docker image (host network), a release tarball with `install.sh` and a systemd user service, and the RDF-SDR edge agent as a systemd service or an ARM image (`packaging/`, `tools/make_release.py`). `packaging/ground-link/` holds host tools for the groundstation's T900 PPP link (diagnosis, a watchdog, an operator command), installed outside Docker; the console itself gets no host control.

This is not a production target tracker, RF range estimator, or general remote-control console. Map overlays are direction helpers, not transmitter locations or distance measurements. The Configuration page settings form is local or dry-run; the only real command is the Kontrol config patch. Read `initialize.md` first; active code and tests override historical documentation. There is no `README.md`.

## Architecture & Data Flow

```text
SDR-DoA Data Out
    -> tools/sdr_doa_collector.py
       bounded GET, schema parsing, redaction, freshness and consistency gates
    -> tools/data_out_reader.py
       one shared collection per refresh interval for every viewer
    -> tools/ground_console.py
       loopback HTTP APIs and frontend/dist static serving
    -> frontend/src/App.tsx
       snapshot/config/MQTT state, local freshness, route and simulation orchestration
    -> page components
       Overview dashboard (map, HUD, node card, layers, Kontrol, polar + spectrum dock),
       health, diagnostics, configuration, monitor, simulation, receiver

Kontrol (Overview, admin) -> POST /api/mqtt/config-patch -> MqttMonitor.publish_config_patch
    -> sdr/v1/uav-01/cmd/config/patch (QoS 1, no retain, 60 s TTL) -> edge agent
    -> ack/config -> ConfigCommandTracker -> GET /api/mqtt/config-patch/<id> -> Kontrol
```

- The collector reads `/status.json`, `/settings.json`, `/DOA_value.html`, and `/doa.xml` only. It enforces host/path, timeout, response-size, numeric, freshness, and native-consistency rules. The host must be in the Data Out host list it is given (`allowed_hosts`: the console passes the saved `console.json` `data_out_hosts`; default `doasdr.local`, `192.168.100.100`, `127.0.0.1`, `localhost`) and the port is always 8081. A `.local` host that the system resolver cannot resolve (the Docker image has no nss-mdns) is looked up once over mDNS by `tools/mdns_resolver.py`, which the console passes as `mdns_resolver` (stdlib, at most 1 s inside the read's budget, strict answer parsing, TTL cache clamped to 5..60 s, failures kept 5 s, never for a request an environment proxy takes); the URL and `Host` header keep the name, the query goes out on every up, multicast-capable IPv4 interface (not only the routing table's choice, which fails on a LAN without a default route), and `collection.host_resolution` records `literal`, `system` or `mdns` with the address, or `proxy` without one. `collect(total_budget_s=...)` bounds one read; failed GETs are not retried, and the other resources are skipped when `status.json` is unreachable. A `NodeProgressTracker` reports a node whose status timestamp, uptime and DAQ frame index stop advancing (`NODE_CLOCK_STALLED` after 10 s; needs two reads). CSV/XML angles are compared only for same-frame pairs (`native_consistency.frame_relation`); adjacent or out-of-window pairs add `NATIVE_ANGLE_UNCHECKED`. DAQ sync failure or ADC overdrive make the snapshot `DEGRADED`. `overall_state` is checked in the order UNAVAILABLE, DEGRADED, INVALID, CONFLICT, STALE, INCOMPLETE, then UNVERIFIED/LIVE. Gate reasons added in the 2026-10 audit fixes: `NODE_CLOCK_STALLED`, `ADC_OVERDRIVE`, `COLLECTION_DEADLINE_EXCEEDED`, `CSV_VIEW_UNAVAILABLE`, `XML_VIEW_UNAVAILABLE`, `NATIVE_ANGLE_INVALID`, `ANGULAR_PEAK_ANGLE_MISMATCH`, `NATIVE_ANGLE_UNCHECKED`; every reason needs EN and ID labels in `lib/i18n.ts`. Display readiness and publication readiness are separate.
- `ground_console.py` is the Python boundary. API routes take precedence over static files, the server refuses non-loopback binds, and the active UI is the built React app. Its static root serves `index.html`, `favicon.ico` and `favicon.svg` (`FRONTEND_ROOT_FILES`; the icons come from `frontend/public/` and `index.html` links both, so the browser never asks for a missing `/favicon.ico`) and `assets/`; `/receiver/` keeps its own root and icon. `--legacy-ui` selects the embedded previous interface. `/api/snapshot` answers from one shared Data Out read per base URL (`tools/data_out_reader.py`, `DataOutReader`): the last collection is kept and every viewer gets it while it is younger, counted from when it started reading the node, than the reuse window `max(1 s, saved refresh interval)`; a viewer that already shows it (it sends the collection `id` back as `seen`) gets a new read once it is 0.25 s short of the window, so one viewer still gets new data on every tick and N viewers polling every T cause one collection per T. `refresh=1` (Refresh, R) reads again only when the last collection is at least 1 s old; `fresh_settings=1` (Kontrol's "Cek ulang") also makes the collector read settings.json, at once when the last collection reused it, otherwise after the same 1 s. Requests that arrive during a collection wait for it (4 s collection budget, so an unreachable Data Out reports UNAVAILABLE in about 4 s), and a failed collection is kept the same way, never longer than the window. The collector reuses a good settings.json (4.7 kB of the about 8 kB a collection reads) for up to 30 s through its `SettingsCache`: not after a node restart (`uptime_ms` went back) or a change of the status.json values that follow the settings, and the same collection reads it after all when the CSV or XML view shows another VFO frequency, VFO count, array or station; the cache is in memory, so the first collection after a console start reads it. Each answer adds `id`, `collected_at_ms`, `age_ms` (time since the collection completed), `shared`, `settings_reused`, `settings_age_ms` and `refresh_seconds` (the saved interval now, which sets the window) to its `collection` block, `settings.reused` and `settings.read_at_ms`, and `reused: true` on a reused `resources["/settings.json"]`. `DataOutReader.read_reason()` is the one place that decides whether a request reads Data Out; reading Data Out only while MQTT is not fresh (#8) goes there. Refresh intervals are 0 (manual), 1, 2, 5, 10 and 30 s, default 2 s, listed by `/api/capabilities`. An explicit `--base-url`, `--mqtt-host`, `--mqtt-port`, `--mqtt-transport` or `--mqtt-ws-path` overrides the saved `console.json` for that run only, so service files and the Docker entrypoint never pass them. When `--config-path` does not exist yet, `main()` builds it from `SDR_DOA_SEED_DATA_OUT_HOSTS` (comma separated, replaces the default host list), `SDR_DOA_SEED_BASE_URL` (checked against the list that applies), `_MQTT_HOST`, `_MQTT_PORT`, `_MQTT_TRANSPORT`, `_MQTT_WS_PATH` and `_REFRESH_SECONDS` (process environment, then `--env-file`; each validated like a saved field, an invalid or empty one, or a host list without the Data Out URL's host, ignored with a warning naming only the variable) and saves it atomically; later starts, even with an invalid file, never use the seed again. A typed `--base-url` must use a host of the saved list (on a first start the one just seeded). The host list is the saved `data_out_hosts` field: 1 to 16 DNS names or IPv4/IPv6 addresses, no wildcards, scheme, port, path or userinfo, deduplicated, always including the host of `base_url`; it is edited in Configuration → Connection & refresh and saved through `POST /api/console-config` with the same gates as `base_url`, and every Data Out check (server start, `/api/console-config`, `/api/snapshot`, the seed, `--base-url`, the collector) uses it. Refusals are 400 with a `DATA_OUT_*` code, the list and the port (see `CLAUDE.md`). `--env-file` (default: the repository `.env`) supplies `SDR_DOA_ADMIN_PASSWORD` and the seeds; `--preferences-path` (default `~/.config/sdr-doa-ground-console/preferences.json`; without it a `GroundConsoleServer` puts `preferences.json` next to `config_path`) holds the browser preferences. `GET /api/tiles/<source>/<z>/<x>/<y>` (`tools/tile_cache.py`, no admin, GET only; a request the browser marks `Sec-Fetch-Site: cross-site` gets 403 `ORIGIN_REJECTED`, so another site cannot make the console fetch tiles) serves the basemap: sources `osm`, `hot`, `imagery`, `imagery-labels`, `topo`, each with fixed upstream templates in Python (HTTPS only, at most two hosts tried one at a time, no redirects, 5 s timeout, 1 MiB cap, `image/png|jpeg|webp` whose bytes match, `User-Agent: SDR-DoA-Ground-Console/<VERSION>`, the standard environment proxy); z/x/y must be canonical integers inside the source's zoom and grid (404 otherwise) and no query, cookie or referrer is forwarded. Tiles are cached as they are viewed under `--tile-cache-dir` (default `~/.cache/sdr-doa-ground-console/tiles`; a `GroundConsoleServer` without it uses `tiles/` next to `config_path`) up to `--tile-cache-max-mb` (512, least recently used first, 0 stores nothing), atomically, never an error body. A tile is fresh for max(upstream max-age, 7 days), capped at 30 days, and served without network while fresh; a stale one is revalidated (ETag/Last-Modified) and served stale when the upstream is unreachable; an uncached one answers 504. A failing host backs off for 30 s, at most 4 upstream fetches run at once, and concurrent requests for one tile share one fetch. Answers carry `Cache-Control: private, max-age=600` (60 for stale) and `X-Tile-Cache: hit|miss|stale`. There is no bulk or area prefetch. Served tiles and 504s are not logged; the cache logs an outage once when it starts and once when it ends. Tests inject loopback upstreams through the constructor's `tile_sources`; no command-line flag changes the upstreams. `GET /api/health` answers `{ok: true, version, receiver_busy}` without reading Data Out or a file (`receiver_busy` comes from an in-memory record of Receiver writes: one in the last 30 s, or an audio session or scan open with a write in the last 120 s) (a healthy check is not logged); `version` comes from the first line of `VERSION` at the repository or install root (`dev` when missing or malformed) and also appears in `/api/capabilities`, with `preferences: true`. `GET /api/preferences` returns `{version, updated_at_ms, values}`; `PUT` or `POST` takes `{values: {key: string|null}}` (null removes a key) and needs the same-origin loopback `Origin` (no admin). `tools/preferences_store.py` keeps only the allowlisted keys (`PREFERENCE_KEYS`, the same list as `lib/preferenceStore.ts`), each as the exact string the browser stores (tokens are short plain words, JSON keys must parse to an object or array, NaN refused), at most 32 KiB per value, 128 KiB in total and a 256 KiB request; an update with any bad entry is refused whole (400 `INVALID_REQUEST`, `PREFERENCE_KEY_UNKNOWN`, `PREFERENCE_VALUE_INVALID`; 413 `PREFERENCE_VALUE_TOO_LARGE`, `PREFERENCES_TOO_LARGE`; 500 `PREFERENCES_WRITE_FAILED`, sent through their own helper so the Kontrol error-code contract does not include them). Writes are atomic with mode 0600; a corrupt or oversized file is kept as `preferences.json.invalid.bak` and the store starts empty. The Receiver routes (`/api/receiver/*`, `tools/receiver_record_store.py` under `--data-dir`, and `tools/receiver_archive.py` for the Records archive) have their own gates: every GET needs `Sec-Fetch-Site` absent, `none` or `same-origin` and one loopback `Host` on the console's port (403 `ORIGIN_REJECTED` otherwise, which also stops DNS rebinding), every POST and DELETE the same-origin loopback `Origin`. The archive routes under `/api/receiver/archive/` are facets, calendar (the browser's own local midnights), timeline, items, scan preview, single audio and scan downloads, POST `exports` (ids or a filter checked against the count the table showed; at most 1000 records and a 4 GiB estimate; a single-use 120 s token) with its streamed GET, POST `delete` (at most 2000) and `retention-preview`; their errors are `{ok:false, code, error}` from `ARCHIVE_ERROR_CODES` and never enter the Kontrol code list. File and ZIP answers follow one streaming rule: checks before the headers, a 60 s write timeout, and no second response once the status line went out (at most 2 ZIPs at once, chunked on HTTP/1.1 for that one response). The Records retention setting (`retention_days`: Off or 1, 3, 7, 14, 30, 60, 90 days, a change needs `confirm: true`) lives in `receiver.sqlite3`; a `RetentionScheduler` thread that `GroundConsoleServer` starts after binding runs a pass 60 s after start and hourly, and a confirmed change runs one pass at once. Without `paho-mqtt` the server still starts and the monitor reports ERROR. Capabilities are honest about the write path: `read_only: false`, `mqtt_publish: true`, `remote_post: false`, `config_apply: false`, `admin_default_password` (boolean only) and a `config_patch` block (`enabled`, `topic`, `qos`, `ttl_ms`, `ranges` from `sdr_doa_mqtt.CONFIG_RANGES`). The `/api/mqtt` monitor snapshot keeps `read_only: true, publish_enabled: false`, because the monitor never publishes on its own.
- The config-patch routes: `GET /api/mqtt/config-reported` (no admin; reported values with the server time each one arrived, `value_received_at_ms`, broker connection and the server-chosen `base_config_rev`, always 200), `POST /api/mqtt/config-patch` (body `{changes, base_config_rev, confirm: true}`, at most 4096 bytes; 202 with `command_id`), and `GET /api/mqtt/config-patch` / `GET /api/mqtt/config-patch/<command_id>` (command status, no admin; the bare path returns the latest command so a reload can resume). POST checks run in a fixed order and the first failure wins: Origin (403 `ORIGIN_REJECTED`), admin (401 `ADMIN_REQUIRED`), request shape, `confirm`, allowlist and ranges (400), monitor present, publish-capable and connected (409/503), base revision known and equal to the request (409 `CONFIG_REVISION_UNKNOWN` / `CONFIG_REVISION_STALE`), no other command in flight (409 `COMMAND_IN_FLIGHT`), then the publish (502 `MQTT_PUBLISH_FAILED`). Error bodies are `{ok: false, code, error, ...}`. `tools/config_command_tracker.py` keeps the last 32 commands on the server and derives each state from what the monitor saw for that id (PUBACK, the broker echo, the agent's ACK): `published`, `delivered`, `acknowledged`, then the final `acked`, `publish_failed` or `no_ack` (expiry plus 5 s). Correlation is server-side because the browser redacts payload keys ending in `id`. The base revision comes from the latest v1 `config_reported`, or a later live v1 `ack_config` (`applied`: its `config_rev`; `conflict`: `current_config_rev`), or else v1 `state`; RDF v2 `rev` is display only. `sdr_doa_lan_agent.py` subscribes to `cmd/config/patch` whenever `--publish` is on and, without `--enable-config`, answers every patch with a `rejected` ACK carrying `REMOTE_CONTROL_DISABLED`.
- `App.tsx` owns lifted application state and the language context. Automatic reads are a `setTimeout` chain; a tick shares a read in flight instead of aborting it (a Refresh or a fresh-settings read runs after a plainer one, `inFlightReadCovers()`), and `displayFresh` depends only on data age and read failure, so Overview does not blank during a refresh. Each read sends the collection id the page shows as `seen`; data age, `localSnapshotFresh` and the top bar's read age count from when the node was read (`snapshotReadAtMonotonic()` in `lib/snapshotRead.ts`: the answer's arrival minus `collection.age_ms`), and the next automatic read starts one interval after the node read when that is earlier than the request (`pollDelayAfterReadMs()`, `startAutomaticReads()`), the first one too (it waits for the read the page started on load or with a new interval and counts from that answer), so every open page follows the console's one Data Out read. When an answer reports a console interval longer than the page's, the page waits for that one; when the interval differs at all (another page changed it), the page re-reads `/api/console-config` once per shared read (`configResyncFor()`) and applies it like its own save, so the top-bar select shows the console's interval. `/api/mqtt` has its own poll (2 s on Message Monitor and System Health, 5 s elsewhere). App also reads `/api/capabilities` once the config is loaded, owns the Overview panel state (`lib/overviewPanels.ts`), the draft that the spectrum dock hands to Kontrol (`lib/controlDraft.ts`), and the console's single Receiver bridge (`createReceiverBridge()` in a ref). The Receiver section mounts lazily, on the first `#/receiver` visit or the first Mulai/Dengar click in the Overview spectrum dock, never at console load (mounting auto-connects an authorized HackRF). After that it stays mounted and hidden, so RX, scans and recordings survive route changes until the console page reloads. `Shell.tsx` provides hash-based routes (`lib/routes.ts`: `ROUTES` in menu order Dashboard, Receiver, System Health, DoA Diagnostics, Configuration, Message Monitor, Simulation; `ROUTE_HASH` writes `#/dashboard` for `overview`; `routeFromHash()` also accepts route ids and older names; `routeShortcut()` is a page's 1-based position) and one top bar on every route: a page-menu button (the popover lists the seven routes by label and key, with the theme toggle and the admin-gated-control chip in its footer; Escape, an outside click, Tab out or a navigation closes it), the brand mark, the route title and read age (not on Overview), the status strip (DATA, DOA, publication gate labelled Delivery/Publikasi, SNAPSHOT, MQTT, SIM), on Overview the panel toggles Lapisan | Polar | Spektrum | Kontrol, the refresh button, a refresh-interval select that saves through the same verified `updateConsoleConfig` path as Configuration, and EN|ID. Keyboard shortcuts are 1–7 pages by their `ROUTES` position (Receiver is 2) and R refresh, also from inside the Receiver frame (`lib/shortcuts.ts`); every key hint, including the spectrum dock's Receiver button, comes from `routeShortcut()`, never a literal; a focused range slider counts as text entry, and digits do not switch pages while focus is inside a container marked `data-no-page-shortcuts` (the basemap radio menu; R still refreshes). Pages, `TacticalMap` (MapLibre) and Plotly are lazy chunks loaded through `lazyWithRetry` and prefetched after load; `LoadErrorBoundary` limits a failed chunk or map crash to its area. `api.ts` uses same-origin requests with timeout, abort, response normalization, and config/branding read-back verification. `main.tsx` calls `startPreferenceSync()` (`lib/preferenceStore.ts`) before the first render: it copies the server's preferences into `localStorage`, waiting at most 800 ms, and uploads keys only this browser has once. Preference modules write through `writePreference()` or the `preferenceStorage()` adapter, which updates `localStorage` and sends the changed keys in one PUT about 500 ms later (retries with backoff, a `keepalive` flush when the page is hidden, nothing sent when the value equals the server copy). The same-origin Receiver frame's own keys (`SDRSetting`, `ReceiverSweepSettings`, `sdr-web-bookmarks`) reach the server through the console's `storage` listener, so only while a console page is open; `browsdr-device-id` and `browsdr-share-code` stay in the browser. A 404 or a non-JSON answer (the Vite dev server) leaves preferences local. Live data never goes through it.
- `OverviewPage` is a full-map dashboard: the map fills the stage (`.ov-map`), the left column holds the `DoaReadout` HUD and the Lapisan panel (`LayersPanel`), the right column holds `NodeCard` and the Kontrol panel (`ControlPanel`), and the bottom dock holds `PolarDock` and `SpectrumDock` (all under `components/overview/` except the HUD). Which panels show, and whether the node card is collapsed, is an operator preference (`sdr-console-overview-panels-v1`, kept on the console through `/api/preferences`; default Polar and Spektrum on, Lapisan and Kontrol off, node card collapsed). With both dock panels off the dock is not rendered. The page measures the floating panels with a ResizeObserver (`lib/mapInsets.ts`) and passes them to the map as padding, so the station is framed in the visible area. `OverviewPage` is memoized so the 500 ms freshness tick in `App.tsx` does not re-render the map or plot; every prop App passes to it must be stable (state, `useCallback` or a ref). One readiness predicate, `overviewDoaStatus()` in `lib/doaStatus.ts`, decides whether DoA is shown; its `shown` gates the HUD bearing, the polar curve and the map overlay (`doaReady`). Bearings are geographic: `geographicBearingForBin(bin, compassOffset)` in `lib/polar.ts` is (360 − θ₀ + offset) mod 360, and θ₀ stays visible as the array-frame value. The HUD shows bearing from north, age (the CSV age plus the shared read's `collection.age_ms`, `ageAtAnswerMs()`, as it was when the answer arrived; marked STALE once the local window closes), θ₀, display peak, offset with its source, and the held reason when DoA is hidden. The dashboard and the page menu carry labels, values, state chips, errors, warnings and prompts that need an action, not one-line explanations or explanatory tooltips; the status-strip tooltips name only a current cause. The node card shows centre frequency and gain from `settings.fields`, the station position (the last live position is held during freshness gaps), and when expanded SNR, DAQ, ADC, DAQ frame, `en_remote_control` and the compass offset; its chip is `overall_state`. On Overview the publication gate shows only in the status strip. `TacticalMap` owns one MapLibre instance, the basemap raster layers, station marker/popup, GeoJSON overlay layers (beam or density heat, lobe, bearing, −3 dB edges, range rings, guides), DOM text labels, a hover/tap readout, `OverlayLegend`, top-centre notices, and its own bottom-left controls (zoom in/out, centre on station, north up, the basemap button, the attribution chip) in place of MapLibre's `NavigationControl`. Basemap styles come from `lib/basemaps.ts`: Standard, Hot, Light, Dark, Satellite, Satellite + labels, Topographic and Plain (labels name the look only; the attribution chip names the data and imagery sources of the drawn style, as their licences require). Every style draws from the console's same-origin `/api/tiles/<source>/{z}/{x}/{y}` route, one URL per source in the browser; the server tries the upstream hosts (`tools/tile_cache.py`). Light and Dark repaint the Standard (`osm`) tiles with raster paint (Dark: brightness-min above brightness-max inverts, hue-rotate 180); Plain loads no tiles. The choice is the `sdr-console-basemap` preference, owned by `OverviewPage` and shared by the map button (a radio menu that is a `popover="manual"` element in the top layer, so the floating panels and the dock never cover it) and a select as the first row of Lapisan; Lapisan's Advanced Reset does not change it. A style change removes and adds only the raster sources and layers under `doa-beam` and never calls `map.setStyle()`, which would drop the GeoJSON data and runtime paint; each style has its own source ids (`bm-<style>`, `bm-<style>-<n>` for label layers), so tile errors of a removed style are ignored by id. Outages are remembered per tile source for the page session; BASEMAP UNAVAILABLE names the style when its tiles fail and none has drawn, BASEMAP PARTIAL when they keep failing (4 within 15 s) while others draw, as offline with part of the view cached (`basemapAfterTile()`, `basemapPartialCheck()`, `basemapAfterView()`, `basemapNotice()` in `lib/map.ts`). Both retry every 60 s without replacing the style; a partial retry is judged 15 s later (no failure clears it, nothing loaded makes it UNAVAILABLE), and a partial style none of whose tiles the view draws any more (MapLibre's renderable tiles of the base source, checked every 5 s) is UNAVAILABLE at once. A partial state is not carried to the next Overview visit. Rings, guides, −3 dB edges and the lobe outline follow the tone of the drawn tiles (light lines on Dark and the imagery styles), and the theme while no tiles are drawn. Overlay settings are controlled by `OverviewPage`: the Lapisan panel has the basemap select, seven visibility toggles (including `edgesVisible` and `labelsVisible`), an `overlayOpacity` slider that scales every paint opacity, and an "Advanced"/"Lanjutan" disclosure that renders the existing `OverlayControls`. The overlay dB scale is Auto (from the vector) by default. Geometry rebuilds are debounced and only touch changed sources; palette, opacity, intensity, and blur are paint-only. MapLibre's worker is bundled by Vite and registered with `setWorkerUrl`; without it, GeoJSON layers never render. The style counts as ready on `styledata` because `load` waits for raster tiles and may never fire offline. The canvas fallback draws on a non-tile error, without WebGL2, after WebGL context loss, or when the worker stalls. The camera is kept across route changes. `PolarPlot` renders with a partial Plotly bundle (`plotly.js/lib/core` + `lib/scatterpolar`, registered in `lib/plotlyPolar.ts`; a Vite plugin drops Plotly's MapLibre CSS) and preserves operator interaction while data updates. Polar mode draws θ₀ counter-clockwise like upstream KrakenSDR; Compass is north-up clockwise. `PolarDock` uses it without its own settings or mode bar and drives `head` and `range` as controlled props; both are part of the layout key and `uirevision`. Its Kompas|Polar switch and the "Adjust"/"Atur" column (Head Up; "Peak up"/"Puncak ke atas", which rotates θ₀ to the top via `peakUpHead()`; dB Auto/Manual; Reset) live in `lib/polarViewSettings.ts` (`sdr-doa-polar-view-v1`) and change only the plot and the HUD display peak. Its compass offset Data Out|Manual writes the Compass source config, which the map and the bearing use too.
- `SpectrumDock` draws a 2 MHz span around the Receiver's RX centre (512 bins, up to 10 fps), or in Spektrum mode the Receiver's wide scan over its own range (512 max-hold bins, up to 10 fps, `receiver:sweep`), and drives the hidden Receiver frame through `lib/receiverBridge.ts`; the protocol is in `lib/receiverBridgeProtocol.ts` and on the frame side in the overlay's `console-bridge.ts` (see `CLAUDE.md`). Header controls: "Follow node frequency"/"Ikuti frekuensi node" (centre from Data Out `settings.fields.center_freq`, VFO from `doa_candidates.csv.frequency_hz_normalized`, fresh data only; `lib/nodeFrequency.ts`), the demodulation mode (NFM, WFM, AM, USB, LSB, DSB, CW, RAW), Listen/Dengar, "Send to RDF-SDR"/"Kirim ke RDF-SDR", Start/Stop (Mulai/Berhenti), "Open full Receiver (2)" (the key from `routeShortcut('receiver')`) and "Adjust"/"Atur". The header order is title, source text or MOCK, tags (UPCONVERTER, SIM, REC), chip, the RX|Spektrum switch ("RX" and "Spektrum"/"Spectrum"), the "Markers"/"Penanda" toggle, then follow, mode, Dengar, Kirim, Mulai, Receiver and Atur. The switch picks what Mulai starts while nothing runs (stored in `sdr-console-spectrum-dock-v1`); the dock shows the mode that runs, so a scan started on the Receiver page appears as Spektrum with live frames (chip `SCAN`, `…` while it starts or stops, `SCAN OFF` when stopped, `SIM` only while a simulated scan starts or runs) and `BUSY` remains only for a scan listen. `DockView` separates `rxRunning` (Dengar, follow-node) from `live` (the trace drawn live, without the stopped overlay). In Spektrum mode Mulai/Berhenti start and stop the scan (`console:sweep-start`/`sweep-stop`), a click or arrow key sets the RX centre and VFO for the next RX (the strongest bin next to the click; arrow step span/200, at least 10 kHz) while the scan keeps running, Dengar stops the scan and starts RX, and ticks and readouts use the decimals the scan's step and bins need; switching modes while something runs stops one and starts the other, asking first in the console page when a scan would end a VFO recording. Below a 1400 px dock (container query on `.ov-spectrum`), follow, mode and Kirim (`.ov-spec-wide`) are hidden in the header and shown in the Atur column (`.ov-spec-narrow`); the source text shows only from 1500 px. The Atur column (`SpectrumSettings.tsx`, 337 px) sits beside the trace, below it on a dock of 760 px or less (in two columns where they fit, never over the trace or the marker row), and the dock grows to fit it only while `DOCK_MAP_KEEP_PX` (256 px) of map stays above it, so the HUD keeps clear of the map buttons and the node card of the legend; beyond that the column scrolls, below the trace together with the trace under the header, and below it when the page stacks (1023 px or less); it holds those copies, the RX dB scale (Auto|Manual, min, max; typed limits apply on Enter or blur), which is the Receiver Dengar tab's own and synced both ways, and the Listener's Sample rate (MSPS), LNA, VGA and +14 dB amp, set through `console:radio` and `console:gains` and disabled with `—` until the frame answers (see `CLAUDE.md`). In Spektrum mode the column holds the scan's dB scale instead (Auto is the dock's own, Manual is the Receiver's Graph min./max., seeded from the status and sent with `console:sweep-display` only when a limit is typed), then Rentang (start and end MHz, "Pusatkan ke RX"), Resolusi (4.88 or 2.44 kHz) and the scan's own LNA, VGA and +14 dB, set with `console:sweep-config` only while no scan runs and shown read-only, tagged "Terkunci selama pindai", while one does (`lib/sweepSettings.ts`); before the frame is mounted they show the Receiver's saved `ReceiverSweepSettings` (`lib/receiverSavedSweep.ts`). A rate change while a VFO recording is armed asks first in the console page; the info line shows the rate, LNA, VGA and +14 dB when the amp is on. Auto keeps the smoothed automatic range; the waterfall keeps its history in dB (`Float32Array`), so Auto and a manual range colour every row with the range in use. A click or arrow key on the trace or waterfall tunes the RX centre and the listen VFO (snapped to 1 kHz) and turns follow-node off; so does a centre or VFO change made on the Receiver page, also while the dock is not mounted (`watchReceiverTuning()` in `lib/receiverSync.ts`, one effect in `App.tsx`, driven by the frame's tune stamps; see `CLAUDE.md`). The Receiver frame owns the centre and the VFO: the dock shows its own tune at once (`displayedTuning()`), then the bridge's `TuneView`, and snaps back when the frame refuses; arrow keys step from the shown value; while RX runs the axis follows the tuned centre at once and a frame taken at the old centre stays drawn at its own frequencies. Before the frame is mounted the dock shows the Receiver's last saved centre and VFO, read only from `SDRSetting` (`lib/receiverSavedTuning.ts`), when follow-node has no node to show. Follow-node and the listen mode are page-wide stores (`followNodeStore`, `listenModeStore` in `lib/listenPrefs.ts`, same preference keys); a mode changed on the Receiver page becomes the stored mode. "Send to RDF-SDR" only opens Kontrol with a draft of `center_frequency_hz` and `vfo_frequency_hz`; it never posts. The Receiver's spectrum markers (its "Penanda spektrum" list, mirrored as `BridgeState.markers` from `receiver:markers`) are drawn in both modes, as lines on the trace and dashed lines on the waterfall in the `--marker` colour, and the Receiver page draws them on its Spektrum canvas and its Dengar trace. Penanda (with the list's count, disabled until the frame answers) turns marking on for this visit only, never saved: a click adds a marker at that frequency through `console:marker-add`, a click next to a marker picks it, and the notice line shows the picked marker with Remove/Hapus and "Tune here"/"Tala ke sini", "Not saved"/"Belum disimpan" while no marker set is selected on the Receiver page, and the last marker error; Enter, `[` `]`, Delete, Ctrl/⌘+Z and Escape work on the focused trace, and marking also works during a wide scan (see `CLAUDE.md`). Spectrum frames go straight from the bridge to canvases, never into React state; only the bridge state (status, `TuneView`, markers, last result) goes through `useSyncExternalStore`, and an open Atur column in Auto gets only the drawn dB range, in whole dB and at most twice a second.
- `ControlPanel` (Kontrol) has admin states `checking`, `locked`, `unlocked` and stages `edit`, `review`, `sending`, `done`. It reads `/api/admin/status` itself (the HttpOnly cookie is shared with Configuration), polls `/api/mqtt/config-reported` every 2 s while unlocked, posts only from the review step with `confirm: true` and the reviewed base revision, then polls the command status every 1 s until it is final. Fields, units (MHz, kHz, dB on screen; Hz and dB on the wire), fallback ranges and the hard-coded list of backend error codes are in `lib/configPatch.ts`.
- Kontrol's current values (form defaults and the review's "from") are MQTT first, then a fresh live Data Out `settings.fields` value for what MQTT does not report. After a final command other than `publish_failed`, Kontrol reads the change back with `lib/configVerify.ts`: per sent field the sent value, the fresh Data Out value (`center_freq` in MHz, `uniform_gain`, `vfo_freq_0`, `vfo_bw_0`, `vfo_squelch_0`; only from a settings.json read at or after the command's `issued_ts_ms`, `settings.read_at_ms`, since the console reuses it for up to 30 s) and the MQTT value, counted only when it arrived after the command's `issued_ts_ms`. Data Out decides when it carries the field; MQTT only otherwise. A field is CONFIRMED within ±500 Hz (frequency), ±1 Hz (bandwidth) or ±0.05 dB, PENDING until 90 s after the final state (no wait when the ACK says the patch was not applied: `rejected`, `conflict`, `expired`, `failed`), then UNCHANGED, or NOT REPORTED when no source carries it. "Cek ulang" re-reads config-reported and Data Out with settings.json (App's `refresh` with `freshSettings`, passed through `OverviewPage` as `onRefreshSnapshot`); Kontrol runs the same read once when a command becomes final. A synthetic snapshot never counts.
- `doaGeometry.ts` generates geodesic bearing, lobe, guide, beam-sector, density-heat, range-ring, and −3 dB edge features, plus the −3 dB width and bearing/distance helpers. `overlayPalette.ts` holds the shared palette stops and MapLibre paint expressions. Signed dB normalization and projection distances are visual parameters, not physical RF conversions.
- `simulation.ts` creates a finite synthetic 360-bin snapshot with publication `BLOCKED` and no authority. `App.tsx` applies it only to Overview; health, diagnostics, runtime, and MQTT remain live, and so do the spectrum dock and Kontrol (follow-node ignores a synthetic snapshot).
- The staging telemetry path is separate: `sdr_doa_lan_agent.py` composes collector gates, safe MQTT contract messages, bounded latest-value queues, and the stdlib MQTT client. `sdr_doa_mqtt_monitor.py` (sdr/v1) and `rdf_node_mqtt_v2.py` (RDF Node v2) share one paho connection that subscribes: transport `tcp` or `websockets` (path `mqtt_ws_path`, default `/mqtt`), a random `groundconsole…` client id, no TLS or credentials. Its only publish is `MqttMonitor.publish_config_patch()`, called by the server for an admin-confirmed patch: QoS 1, `retain=False`, `MessageExpiryInterval` equal to the 60 s TTL, and only while connected with every SUBACK in, so paho never queues a command for replay after a reconnect. PUBACKs arrive through `on_publish`; `wait_for_publish` is never called under the monitor lock. The monitor also keeps a bounded record of v1 `config_reported`, `state`, `ack_config` and echoed `config_patch` messages for the config-patch path, outside the Message Monitor snapshot. Message Monitor shows per-kind counts, ages and STALE marks, and an RDF Node v2 panel that polls `GET /api/mqtt/rdf-node` every 2 s while the page is open.

## Development Commands

Install and validate the frontend from `frontend/`:

```sh
cd frontend
npm ci --ignore-scripts --no-audit --no-fund
npm run check       # TypeScript build/typecheck, not lint
npm test            # Vitest run
npm run build       # tsc -b && vite build; empties and rewrites frontend/dist, including dist/receiver
npm run build:all   # npm run build, then tools/build_browsdr_receiver.py (needs vendor/BrowSDR)
npm run dev         # Vite development server on 127.0.0.1
npm run preview     # Vite preview on 127.0.0.1
```

Run the production UI through the Python server from the repository root:

```sh
.venv/bin/python tools/ground_console.py --bind 127.0.0.1 --port 8787
# legacy embedded UI, when specifically needed
.venv/bin/python tools/ground_console.py --legacy-ui --bind 127.0.0.1 --port 8787
```

The default URL is `http://127.0.0.1:8787/`. Vite alone does not provide the `/api` backend. Never expose the Ground Console or Vite server on a non-loopback address.

Release and packaging (Linux; details in `QUICKSTART.md` and `packaging/*/README.md`):

```sh
python3 tools/make_release.py                 # npm ci + build:all, then both tarballs in dist/release
python3 tools/make_release.py --skip-build    # package the existing frontend/dist
docker compose up -d --build                  # console image from a regular clone (host network, volume /data)
sudo sh packaging/docker/sdr-doa-docker install --auto-update   # console from the GHCR image, daily update with rollback
sh packaging/console/install.sh --help        # native install: venv, systemd user service, sdr-doa-console
sdr-doa-console update --check                # native install: newest release of the same major; auto-update on|off|status
sudo sh packaging/agent/install-agent.sh --dry-run   # RDF-SDR agent as a systemd service
sudo sh packaging/ground-link/install.sh --dry-run   # T900 PPP link diag, watchdog and t900-link on the groundstation host
```

A GitHub Release comes from CI, not from a local build: bump `VERSION` on main together with the files that name it (every release: the `image:` tags of `docker-compose.yml`, `docker-compose.release.yml` and `docker-compose.agent.yml` and `sdr-doa-agent:<V>` in `Dockerfile.agent`; a new major also `DEFAULT_CHANNEL` in `packaging/docker/sdr-doa-docker`, `${SDR_DOA_IMAGE_TAG:-N}` in `docker-compose.ghcr.yml` and the channel text of the script, that compose file and the docs; the tests fail otherwise), then push the tag `v<VERSION>` (`git tag v2.0.0 && git push origin v2.0.0`) or run the Release workflow on main. `release.yml` tests the tree, builds the tarballs with `make_release.py --with-wheels`, publishes `sdr-doa-ground-console-<V>-linux.tar.gz`, `sdr-doa-rdf-sdr-agent-<V>.tar.gz`, `sdr-doa-docker` and `SHA256SUMS`, and then pushes `ghcr.io/sanadunt/sdr-doa-ground-console` (amd64, arm64) and `ghcr.io/sanadunt/sdr-doa-rdf-sdr-agent` (amd64, arm64, arm/v7) built from those tarballs, tagged `<V>`; the channel tags `<MAJOR>.<MINOR>`, `<MAJOR>` and `latest` move to it only when no higher stable release they cover exists (a prerelease gets only `<V>`). Whoever can push a tag or write packages reaches every auto-updating host; `QUICKSTART.md` ("Rilis di GitHub") lists the GitHub settings that limit that.

Installs update without a GitHub login, because the repository, its release assets and (once set Public) the GHCR packages are public. Docker: `sdr-doa-docker update` pulls the channel tag (default the major), waits for the health check, puts the previous image back when the new one fails and records an image that failed its health check so the daily `sdr-doa-docker-update.timer` skips it; `--auto` also skips an image older than the running one. Native: `sdr-doa-console update` reads the latest release from the GitHub API, checks `SHA256SUMS` and `MANIFEST.sha256`, runs that release's `install.sh` with the recorded options and restores the previous program when `/api/health` does not report the new version; `sdr-doa-console-update.timer` runs it daily (`update --auto`). Both timers wait while `/api/health` reports `receiver_busy` (a Receiver recording or scan archive), at most 7 days. The native agent service has no updater (run the new installer); its Docker variant updates like the console. See `CLAUDE.md` ("Settings persistence and Linux packaging", "CI and releases").

Every launch path (Docker entrypoint, systemd unit, `sdr-doa-console run`) passes `--bind 127.0.0.1` and one data directory: `--config-path DATA/console.json --branding-path DATA/branding.json --preferences-path DATA/preferences.json --data-dir DATA/receiver --tile-cache-dir DATA/tiles --env-file DATA/.env`, with DATA = `/data` in Docker or `~/.local/share/sdr-doa-ground-console` natively. Docker runs as uid 10001 with `network_mode: host`; never publish ports from a bridge network.

## Code Conventions & Common Patterns

- TypeScript is strict. Normalize external values from `unknown`, then apply finite/range checks. Represent unavailable, stale, conflict, and error states explicitly instead of coercing bad data into valid-looking values.
- UI text lives in `lib/i18n.ts` with English and Indonesian dictionaries; read it through `useI18n()`. Add every key to both dictionaries (`i18n.test.ts` enforces key and placeholder parity). Status codes such as `STALE` or `BLOCKED` stay untranslated. The language choice is stored in `localStorage` under `sdr-console-lang` and synced to the console like the other preferences.
- Use pure helpers for contracts and transformations. Keep API validation in `api.ts`, telemetry readiness/gate logic in `lib/telemetry.ts`, GPS selection in `lib/map.ts`, angle conversion in `lib/polar.ts`, and GeoJSON math in `lib/doaGeometry.ts`.
- React state is lifted into `App.tsx` and passed through callback props. Effects must clean up timers, abort controllers, observers, MapLibre resources, Plotly instances, and listeners because the app mounts under `StrictMode`.
- Preserve latest-request-wins behavior and local freshness expiry. Do not recreate map/plot layout or camera state for ordinary data updates. Use `localStorage` only for operator preferences (theme, language, basemap style, overlay settings, GPS/Compass source choice, Overview panels and node-card collapse, polar view, listen mode, follow-node, the spectrum dock's mode, scan dB Auto choice and last known RX dB scale), with validation on restore and every access in try/catch. Write them through `writePreference()` or `preferenceStorage()` so they reach `/api/preferences`; a new key must be added to `PREFERENCE_KEYS` in both `lib/preferenceStore.ts` and `tools/preferences_store.py` (the contract test compares them). Never put secrets, credentials or live data in a preference.
- Components use `PascalCase`; functions, variables, and hooks use `camelCase`; constants use `UPPER_SNAKE_CASE`; Python modules/functions use `snake_case`; Python tests use `test_*` entry points.
- Python paths are intentionally bounded and defensive: allowlisted URLs, no redirects, finite timeouts, body limits, redaction, atomic local writes, and explicit loopback checks. MQTT payloads are schema-validated, size-bounded, and latest-value-wins per stream.
- Keep live, fixture, and synthetic data separate. Simulation must remain visibly labeled `SIMULATION` and must not affect health, diagnostics, MQTT, publication authority, or Raspberry state.
- Preserve the freshness gate, publication gate, redaction, CSP, timeout/abort handling, the monitor's rule that it never publishes on its own, and the dry-run boundary of the Configuration form. The one remote write is the Kontrol config patch (`POST /api/mqtt/config-patch` to `cmd/config/patch`). Keep all of its rules: loopback bind only; a port-exact same-origin loopback `Origin` header (no header or another origin gives 403 before the body is read); the admin cookie; `confirm: true` sent only after the UI review step; the server-side allowlist and `CONFIG_RANGES`; the reviewed `base_config_rev` must equal the server's; QoS 1, never retained, 60 s TTL (also as `MessageExpiryInterval`); at most one non-final command at a time; publish only while the monitor is connected with its subscriptions acknowledged; no MQTT in the browser and no MQTT credentials in the console. `POST /api/admin/login`, `/api/admin/logout`, `/api/console-config`, `/api/mqtt/connect` and `PUT`/`POST /api/preferences` also require that same-origin loopback `Origin` (403 `ORIGIN_REJECTED`), because they control the admin session and the MQTT monitor that carries the patch; failed logins from other origins never reach the login throttle. The console itself never publishes the bearing. Do not add another remote write path, and do not expose secrets to `VITE_*` or browser state.
- Styles load in `main.tsx` as `styles.css`, then `console-design.css`, then `polar-layout.css`, then `overview-dashboard.css` (the `.ov-*` dashboard classes, `--ov-dock-h`, `--ov-gap`), then `page-kit.css` (the `.pg-*` page kit: `--pg-*` tokens, page bar, 12-column grid with spans 3/4/5/6/7/8/12 that become 6 or 12 below 1280 px and one column below 1024 px, cards, stat tiles, key/value grids, tables that stack into cards at 600 px and below, fields, switches, notices; console tokens only, no literal colours). Later files override earlier declarations. Non-dashboard pages carry no footer, eyebrow or description: their H1 is the page bar's title, visually hidden above 600 px where the top bar names the page, and shown with the read age at 600 px and below, where the top-bar title is hidden. Like the Dashboard, their cards carry labels, values, chips, errors, warnings and prompts that need an action, and a result says what happened in a few words ("Monitor restarted."); a tooltip names only a current cause, such as the stalled or regressed counters on System Health's progress value, never what a state or a button means. Dashboard touch targets are at least 44 px. At 1023 px or less the dashboard stacks in normal flow (map, HUD, Lapisan, node card, Kontrol, Polar, Spektrum) and the page scrolls; at 600 px or less it uses a 16 px side gutter. Check responsive and reduced-motion behavior when changing UI.

## Runtime/Tooling Preferences

- Use npm from `frontend/` with the committed lockfile. Project docs recommend Node 22.12+ within a supported Node 22 LTS; Vite/plugin engine ranges also accept newer supported Node versions. No root package manager, `.nvmrc`, or npm version is pinned.
- Use the project `.venv` for Python commands, Python 3.9 or newer (the console imports `zoneinfo` through the Receiver store). The Python tools are mostly standard-library code. `paho-mqtt==2.1.0` is needed for the MQTT monitor, synthetic publisher, and related tests; without it the console starts with the monitor in ERROR. On Windows, `tzdata` only makes the local times in Receiver ZIP file names follow the browser's zone; the Records calendar and time ranges use the browser's own day bounds.
- There is no Python dependency manifest for development (only `packaging/console/requirements.txt` for installs), and no formatter, linter, or coverage configuration. GitHub Actions runs the verification sequence (`.github/workflows/ci.yml`) and publishes releases (`release.yml`); see `CLAUDE.md`, "CI and releases". Docker and Compose files exist for Linux deployment only. `npm run check` is the defined static check; there is no `npm run lint`.
- Build `frontend/dist` with `npm run build:all` before full static-serving QA. The static regression suite skips build-dependent checks when `frontend/dist/index.html` is absent, and fails its Receiver checks when `frontend/dist` exists and `vendor/BrowSDR` is checked out but `frontend/dist/receiver` is missing.
- Keep credentials in the process environment or the env file (`--env-file`, default the ignored root `.env`). `SDR_DOA_ADMIN_PASSWORD` is Python-only; never rename it to a `VITE_` variable or embed it in the frontend bundle. The process environment wins over the env file. When the variable is absent from both, the default password `123456` applies: the server prints a startup warning, capabilities report `admin_default_password: true` (never the password), and Kontrol shows a warning. An explicitly empty value (`SDR_DOA_ADMIN_PASSWORD=`) disables admin login (503 `ADMIN_DISABLED`). A `.env` that exists but cannot be read or decoded also disables login instead of falling back to the default. After 5 failed logins within 60 s, every login, the correct one included, gets 429 `ADMIN_LOGIN_THROTTLED` for 30 s (counted for the whole server). The admin session is an HttpOnly, SameSite=Strict cookie with a 30 min TTL; it unlocks branding and Kontrol. Password changes need a console restart.
- Local console defaults are loopback bind `127.0.0.1`, port `8787`, Data Out `http://doasdr.local:8081` (hosts from the saved `data_out_hosts` list, default `doasdr.local`, `192.168.100.100`, `127.0.0.1`, `localhost`; port 8081 only), and MQTT `10.90.0.1:9001` over WebSocket. The MQTT host may be any IPv4/IPv6 literal or `localhost` (no DNS names); the console opens an outbound MQTT connection there (it subscribes, and publishes only an admin-confirmed config patch) while its own HTTP bind stays loopback. A Kontrol send works only through a broker that accepts this anonymous, non-TLS client and lets it publish to `sdr/v1/uav-01/cmd/config/patch`. Staging broker files are not production security configurations.
