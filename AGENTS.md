# Repository Guidelines

## Project Overview

This repository is a local, loopback-only Ground Console for SDR-DoA observation. It answers the Dashboard from the RDF Node's MQTT telemetry while that is fresh and otherwise from bounded Data Out (fallback) resources (`tools/telemetry_source.py`), validates health and freshness, keeps native CSV/XML candidates separate, exposes publication-gate reasons, and renders the result in a React UI. The UI also provides a browser-only DoA simulation, local branding/configuration, renderer-only GPS/Compass choices, an optional MQTT monitor (the RDF Node edge contract of `docs/MQTT_KONTRAK.md`, root `sdr/v2/uav-01`; the one MQTT, with Data Out as the fallback, `docs/KEPUTUSAN_MQTT.md`), and an embedded BrowSDR Receiver (route 2, see `CLAUDE.md`) that the Dashboard spectrum dock drives through a postMessage bridge. The Overview route (id `overview`, `OverviewPage`, `ov-*` classes) is labelled Dashboard in the UI and lives at `#/dashboard`; `#/overview` still opens it. The UI calls the Raspberry node RDF-SDR and the HackRF receiver RadioSpectrum (labels only; identifiers, API fields, MQTT topics and the WebUSB filters keep their names, and the browser's own USB chooser still shows the USB product name). The monitor subscribes and never publishes on its own. The console has exactly one remote write path: the Kontrol panel on the Dashboard, which publishes admin-gated RDF Node commands in the edge's own format (`docs/MQTT_KONTRAK.md` section 9): an explicitly confirmed `config.patch` on `sdr/v2/<node>/cmd/config/patch`, and `config.get` on `cmd/config/get`, which asks the node for its settings. The RDF Node edge decides whether to apply a patch and answers on `ack/config`. Its one write to its own host is the top bar's Restart and Shutdown (the owner's decision of 2026-10-31): on the console's own loopback page only, after a confirmation in the page, `POST /api/host/power` writes a request file holding `reboot` or `poweroff` that the host side in `packaging/host-power` (a systemd `.path` unit and a root oneshot) acts on; the LAN view gets neither the buttons nor the route. Everything the operator saves (connection, MQTT, refresh interval, branding, the admin password in an env file, Receiver records and their Records retention setting, and the browser UI preferences through `/api/preferences`) lives in files on the console host, so it survives another browser, a cleared cache and a container rebuild. The console binds loopback only, with one opt-in exception: the read-only LAN view (`lan_access` in `console.json`, `tools/lan_access.py`), a second listener of the same process that an admin enables in Configuration and that serves the built UI and a read-only list of API routes to the client addresses the operator allowed, so a tablet can watch the console without any write path. Linux packaging ships the console as a Docker image (host network) and a release tarball with `install.sh` and a systemd user service (`packaging/`, `tools/make_release.py`). The Raspberry runs the RDF Node edge (`sanadunt/rdf-indicator-raspberry`); since 3.0.0 this repository ships no edge agent of its own (`CHANGELOG.md`). `packaging/ground-link/` holds host tools for the groundstation's T900 PPP link (diagnosis, a watchdog, an operator command), installed outside Docker. Apart from the power request the console gets no host control: no Docker socket, D-Bus, polkit, capabilities or port.

This is not a production target tracker, RF range estimator, or general remote-control console. Map overlays are direction helpers, not transmitter locations or distance measurements. The Configuration page settings form is local or dry-run (its dry-run previews the RDF Node config.patch envelope without sending it); the only real commands are Kontrol's config.patch and config.get. Read `initialize.md` first; active code and tests override historical documentation. How the console treats imperfect data (read leniently, label instead of rejecting, keep data flowing, operator-language failures) and what is never loosened is `docs/PRINSIP_DATA.md`; follow it when adding a validator, a display condition or a Kontrol message. There is no `README.md`.

## Architecture & Data Flow

```text
RDF Node edge (MQTT, sdr/v2/uav-01) -> sdr_doa_mqtt_monitor.py + rdf_node_mqtt_v2.py
    -> tools/telemetry_source.py
       MQTT fresh: a TelemetrySnapshot from LIVE DoA, LIVE Angular and health
SDR-DoA Data Out (fallback)
    -> tools/sdr_doa_collector.py
       bounded GET, schema parsing, redaction, freshness and consistency gates;
       only a light read (status.json, settings.json, doa.xml) while MQTT is fresh
    -> tools/data_out_reader.py
       the source of each answer; one shared collection per refresh interval for every viewer
    -> tools/ground_console.py
       loopback HTTP APIs and frontend/dist static serving
    -> frontend/src/App.tsx
       snapshot/config/MQTT state, local freshness, route and simulation orchestration
    -> page components
       Overview dashboard (map, HUD, node card, layers, Kontrol, polar + spectrum dock),
       health, diagnostics, configuration, monitor, simulation, receiver

Receiver frame (groundstation page) -> lib/receiverMirrorPublisher.ts -> POST /api/mirror/receiver
    -> tools/receiver_mirror.py (memory only) -> GET /api/mirror/receiver (loopback and LAN view)
    -> lib/receiverMirrorFeed.ts -> MIRROR spectrum dock and Receiver route in the LAN view

Kontrol (Overview, admin) -> POST /api/mqtt/config-patch | config-get -> rdf_node_commands.build_command
    -> MqttMonitor.publish_rdf_node_command -> sdr/v2/uav-01/cmd/config/patch | cmd/config/get
       (QoS 1, no retain, 15 s TTL) -> RDF Node edge
    -> ack/config, settings/reported -> ConfigCommandTracker -> GET /api/mqtt/config-patch/<id>,
       GET /api/mqtt/config-reported -> Kontrol
```

- The collector reads `/status.json`, `/settings.json`, `/DOA_value.html`, and `/doa.xml` only. It enforces host/path, timeout, response-size, numeric, freshness, and native-consistency rules. The host must be in the Data Out host list it is given (`allowed_hosts`: the console passes the saved `console.json` `data_out_hosts`; default `doasdr.local`, `192.168.100.100`, `127.0.0.1`, `localhost`) and the port is always 8081. A `.local` host that the system resolver cannot resolve (the Docker image has no nss-mdns) is looked up once over mDNS by `tools/mdns_resolver.py`, which the console passes as `mdns_resolver` (stdlib, at most 1 s inside the read's budget, strict answer parsing, TTL cache clamped to 5..60 s, failures kept 5 s, never for a request an environment proxy takes); the URL and `Host` header keep the name, the query goes out on every up, multicast-capable IPv4 interface (not only the routing table's choice, which fails on a LAN without a default route), and `collection.host_resolution` records `literal`, `system` or `mdns` with the address, or `proxy` without one. `collect(total_budget_s=...)` bounds one read; failed GETs are not retried, and the other resources are skipped when `status.json` is unreachable. A `NodeProgressTracker` reports a node whose status timestamp, uptime and DAQ frame index stop advancing (`NODE_CLOCK_STALLED` after 10 s; needs two reads). CSV/XML angles are compared only for same-frame pairs (`native_consistency.frame_relation`); adjacent or out-of-window pairs add `NATIVE_ANGLE_UNCHECKED`. DAQ sync failure or ADC overdrive make the snapshot `DEGRADED`. Parsing is lenient (`docs/PRINSIP_DATA.md`): status.json needs only `timestamp_ms` (0/1 booleans are `coerced_fields`, a field of the wrong type is left out in `partial_fields`, missing DAQ fields make the DAQ health `UNKNOWN` with `DAQ_HEALTH_UNKNOWN`, an overdrive nothing reports is `adc_not_overdriven: null` with `ADC_OVERDRIVE_UNKNOWN`); CSV and XML need only the time, the angle and the CSV's 360-bin vector, other columns read as null in `missing_fields`; a multi-VFO CSV without one XML match uses the VFO 0 row (`csv_row_selection` `first_row_unconfirmed`, `CSV_VFO_ROW_UNCONFIRMED`). A failed light read keeps the last good one while its values count (65 s, `data_out_light.kept_previous`). `overall_state` is checked in the order UNAVAILABLE, DEGRADED, INVALID, CONFLICT, STALE, INCOMPLETE, then UNVERIFIED/LIVE. Gate reasons added in the 2026-10 audit fixes: `NODE_CLOCK_STALLED`, `ADC_OVERDRIVE`, `COLLECTION_DEADLINE_EXCEEDED`, `CSV_VIEW_UNAVAILABLE`, `XML_VIEW_UNAVAILABLE`, `NATIVE_ANGLE_INVALID`, `ANGULAR_PEAK_ANGLE_MISMATCH`, `NATIVE_ANGLE_UNCHECKED`; every reason needs EN and ID labels in `lib/i18n.ts`. Display readiness and publication readiness are separate.
- `ground_console.py` is the Python boundary. API routes take precedence over static files, the server refuses non-loopback binds (the LAN view below is a second listener, never this one's bind), and the active UI is the built React app. Its static root serves `index.html`, `favicon.ico` and `favicon.svg` (`FRONTEND_ROOT_FILES`; the icons come from `frontend/public/` and `index.html` links both, so the browser never asks for a missing `/favicon.ico`) and `assets/`; `/receiver/` keeps its own root and icon. `--legacy-ui` selects the embedded previous interface. `/api/snapshot` answers from one shared Data Out read per base URL (`tools/data_out_reader.py`, `DataOutReader`): the last collection is kept and every viewer gets it while it is younger, counted from when it started reading the node, than the reuse window `max(1 s, saved refresh interval)`; a viewer that already shows it (it sends the collection `id` back as `seen`) gets a new read once it is 0.25 s short of the window, so one viewer still gets new data on every tick and N viewers polling every T cause one collection per T. `refresh=1` (Refresh, R) reads again only when the last collection is at least 1 s old; `fresh_settings=1` (Kontrol's "Cek ulang") also makes the collector read settings.json, at once when the last collection reused it, otherwise after the same 1 s. Requests that arrive during a collection wait for it (4 s collection budget, so an unreachable Data Out reports UNAVAILABLE in about 4 s), and a failed collection is kept the same way, never longer than the window. The collector reuses a good settings.json (4.7 kB of the about 8 kB a collection reads) for up to 30 s through its `SettingsCache`: not after a node restart (`uptime_ms` went back) or a change of the status.json values that follow the settings, and the same collection reads it after all when the CSV or XML view shows another VFO frequency, VFO count, array or station; the cache is in memory, so the first collection after a console start reads it. Each answer adds `id`, `collected_at_ms`, `age_ms` (time since the collection completed), `shared`, `settings_reused`, `settings_age_ms`, `refresh_seconds` (the saved interval now, which sets the window) and `console_base_url` (the console's Data Out URL now) to its `collection` block, `settings.reused` and `settings.read_at_ms`, and `reused: true` on a reused `resources["/settings.json"]`. `DataOutReader.read_reason()` is the one place that decides whether a request reads Data Out. MQTT comes first (issue #8, `tools/telemetry_source.py`, contract in `docs/MQTT_KONTRAK.md` section 8): while the RDF Node store holds a `state` session and a `telemetry/health` of it received at most 8 s ago with `daq=1` (the store takes health only with an advancing `q`; a connection alone is not enough), every answer is built from MQTT (`mqtt_snapshot()`, fed by `MqttMonitor.rdf_node_view()`) and no full collection runs. That answer has the TelemetrySnapshot shape with one DoA view, `doa_candidates.mqtt`: θ₀, frequency, PAPR and power from LIVE `telemetry/doa` (`ok=1`; θ₀ only while this session's `capabilities.angle` is `theta_mirror` or `csv_native`, else `MQTT_ANGLE_CONVENTION_UNKNOWN`), the 360-bin vector from LIVE `telemetry/angular` (`flags=63`) with the same frequency and revision (a frame of an older `q` only while its peak is within 3° of the DoA's θ₀, with `NATIVE_ANGLE_UNCHECKED`; further away `PEAK_MOVED`, no vector, so the bearing and the curve never point apart; a LIVE DoA without a paired frame is still shown, `UNVERIFIED` with `MQTT_ANGULAR_UNAVAILABLE`, its bearing on the HUD and the map without the curve, because the edge sends Angular about every 9 s and none for 20 s after a command or reconnect, section 8.3a), `native_consistency` from the DoA against its Angular frame (same `q` is one record, so angles more than 1° apart are `CONFLICT`), the DAQ state from health, `collection.age_ms` 0 and a new `id` per answer. `ok=0`, trust-only Angular and both diagnostic topics stay in its `mqtt` diagnostics block and never fill a candidate (`MQTT_DOA_UNVERIFIED`, `MQTT_NO_DOA`, `MQTT_ANGULAR_UNAVAILABLE`, `MQTT_DOA_ANGULAR_CONFLICT`). The boundary stays: authority none, clock `remote_unverified`, gate `BLOCKED`, never `LIVE`. What MQTT never carries (position from doa.xml `LOCATION`, the settings fields, ADC overdrive and SNR; the edge's `ok=1` does not weigh the overdrive) comes from a light read (`collect_light()`: status.json, settings.json through the `SettingsCache`, doa.xml, about 5.8 kB, kept in the `data_out_light` block; all of it counts for 65 s and answers as not read once older, `expired`; settings.json is read after all when doa.xml shows another frequency or station) that runs in a background thread first, then at most every 30 s (`LIGHT_READ_INTERVAL_S`), at once (at most once a second) when the session or `state.cfg` changes, then reading settings.json instead of reusing it, and for `fresh_settings`, which waits for it; Refresh reads no Data Out then. So an MQTT answer's overdrive verdict is up to 30 s old (accepted, to spare the T900 link); without a current light read it is unknown (`checks.adc_not_overdriven` null, gate reason `ADC_OVERDRIVE_UNKNOWN`), and the Dashboard still draws the bearing but shows DOA `DEGRADED` with that cause (`adcOverdriveUnknown()` in `lib/telemetry.ts`), while `overall_state` stays `UNVERIFIED`. When MQTT is not fresh the request reads Data Out fully as before. Every answer carries `source` (`kind` `mqtt`, `data_out` or `none`, `reason`, `reasons`, `mqtt` and `data_out` summaries): `MQTT_FRESH`, or why not (`MQTT_DISABLED`, `MQTT_NO_SESSION`, `MQTT_NO_HEALTH`, `MQTT_HEALTH_STALE`, `MQTT_DAQ_NOT_HEALTHY`, `DATA_OUT_REQUESTED`), plus `DATA_OUT_UNAVAILABLE` when Data Out did not answer either (`none`); every source reason and `MQTT_*` gate reason needs EN and ID labels in `lib/i18n.ts`. The legacy UI sends `source=data_out` and always gets Data Out; the LAN view ignores that flag. Refresh intervals are 0 (manual), 1, 2, 5, 10 and 30 s, default 2 s, listed by `/api/capabilities`. An explicit `--base-url`, `--mqtt-host`, `--mqtt-port`, `--mqtt-transport` or `--mqtt-ws-path` overrides the saved `console.json` for that run only and is never written to it: `main()` passes the saved copy as `saved_config`, and every save (`/api/console-config`, `/api/lan-access`) writes only the fields it changes into that copy (`_saved_copy_locked()`; a host list without the saved URL's host saves the URL in use); service files and the Docker entrypoint never pass them. When `--config-path` does not exist yet, `main()` builds it from `SDR_DOA_SEED_DATA_OUT_HOSTS` (comma separated, replaces the default host list), `SDR_DOA_SEED_BASE_URL` (checked against the list that applies), `_MQTT_HOST`, `_MQTT_PORT`, `_MQTT_TRANSPORT`, `_MQTT_WS_PATH` and `_REFRESH_SECONDS` (process environment, then `--env-file`; each validated like a saved field, an invalid or empty one, or a host list without the Data Out URL's host, ignored with a warning naming only the variable) and saves it atomically; later starts, even with an invalid file, never use the seed again. A typed `--base-url` must use a host of the saved list (on a first start the one just seeded). The host list is the saved `data_out_hosts` field: 1 to 16 DNS names or IPv4/IPv6 addresses, no wildcards, scheme, port, path or userinfo, deduplicated, always including the host of `base_url`; it is edited in Configuration → Connection & refresh and saved through `POST /api/console-config` with the same gates as `base_url`, and every Data Out check (server start, `/api/console-config`, `/api/snapshot`, the seed, `--base-url`, the collector) uses it. Refusals are 400 with a `DATA_OUT_*` code, the list and the port (see `CLAUDE.md`). `--env-file` (default: the repository `.env`) supplies `SDR_DOA_ADMIN_PASSWORD` and the seeds; `--preferences-path` (default `~/.config/sdr-doa-ground-console/preferences.json`; without it a `GroundConsoleServer` puts `preferences.json` next to `config_path`) holds the browser preferences. `GET /api/tiles/<source>/<z>/<x>/<y>` (`tools/tile_cache.py`, no admin, GET only; a request the browser marks `Sec-Fetch-Site: cross-site` gets 403 `ORIGIN_REJECTED`, so another site cannot make the console fetch tiles) serves the basemap: sources `osm`, `hot`, `imagery`, `imagery-labels`, `topo`, each with fixed upstream templates in Python (HTTPS only, at most two hosts tried one at a time, no redirects, 5 s timeout, 1 MiB cap, `image/png|jpeg|webp` whose bytes match, `User-Agent: SDR-DoA-Ground-Console/<VERSION>`, the standard environment proxy); z/x/y must be canonical integers inside the source's zoom and grid (404 otherwise) and no query, cookie or referrer is forwarded. Tiles are cached as they are viewed under `--tile-cache-dir` (default `~/.cache/sdr-doa-ground-console/tiles`; a `GroundConsoleServer` without it uses `tiles/` next to `config_path`) up to `--tile-cache-max-mb` (512, least recently used first, 0 stores nothing), atomically, never an error body. A tile is fresh for max(upstream max-age, 7 days), capped at 30 days, and served without network while fresh; a stale one is revalidated (ETag/Last-Modified) and served stale when the upstream is unreachable; an uncached one answers 504. A failing host backs off for 30 s, at most 4 upstream fetches run at once, and concurrent requests for one tile share one fetch. Answers carry `Cache-Control: private, max-age=600` (60 for stale) and `X-Tile-Cache: hit|miss|stale`. There is no bulk or area prefetch. Served tiles and 504s are not logged; the cache logs an outage once when it starts and once when it ends. Tests inject loopback upstreams through the constructor's `tile_sources`; no command-line flag changes the upstreams. `GET /api/health` answers `{ok: true, version, receiver_busy}` without reading Data Out or a file (`receiver_busy` comes from an in-memory record of Receiver writes: one in the last 30 s, or an audio session or scan open with a write in the last 120 s) (a healthy check is not logged); `version` comes from the first line of `VERSION` at the repository or install root (`dev` when missing or malformed) and also appears in `/api/capabilities`, with `preferences: true`. `GET /api/preferences` returns `{version, updated_at_ms, values}`; `PUT` or `POST` takes `{values: {key: string|null}}` (null removes a key) and needs the same-origin loopback `Origin` (no admin). `tools/preferences_store.py` keeps only the allowlisted keys (`PREFERENCE_KEYS`, the same list as `lib/preferenceStore.ts`), each as the exact string the browser stores (tokens are short plain words, JSON keys must parse to an object or array, NaN refused), at most 32 KiB per value, 128 KiB in total and a 256 KiB request; an update with any bad entry is refused whole (400 `INVALID_REQUEST`, `PREFERENCE_KEY_UNKNOWN`, `PREFERENCE_VALUE_INVALID`; 413 `PREFERENCE_VALUE_TOO_LARGE`, `PREFERENCES_TOO_LARGE`; 500 `PREFERENCES_WRITE_FAILED`, sent through their own helper so the Kontrol error-code contract does not include them). Writes are atomic with mode 0600; a corrupt or oversized file is kept as `preferences.json.invalid.bak` and the store starts empty. The Receiver routes (`/api/receiver/*`, `tools/receiver_record_store.py` under `--data-dir`, and `tools/receiver_archive.py` for the Records archive) have their own gates: every GET needs `Sec-Fetch-Site` absent, `none` or `same-origin` and one loopback `Host` on the console's port (403 `ORIGIN_REJECTED` otherwise, which also stops DNS rebinding), every POST and DELETE the same-origin loopback `Origin`. The archive routes under `/api/receiver/archive/` are facets, calendar (the browser's own local midnights), timeline, items, scan preview, single audio and scan downloads, POST `exports` (ids or a filter checked against the count the table showed; at most 1000 records and a 4 GiB estimate; a single-use 120 s token) with its streamed GET, POST `delete` (at most 2000) and `retention-preview`; their errors are `{ok:false, code, error}` from `ARCHIVE_ERROR_CODES` and never enter the Kontrol code list. File and ZIP answers follow one streaming rule: checks before the headers, a 60 s write timeout, and no second response once the status line went out (at most 2 ZIPs at once, chunked on HTTP/1.1 for that one response). The Records retention setting (`retention_days`: Off or 1, 3, 7, 14, 30, 60, 90 days, a change needs `confirm: true`) lives in `receiver.sqlite3`; a `RetentionScheduler` thread that `GroundConsoleServer` starts after binding runs a pass 60 s after start and hourly, and a confirmed change runs one pass at once. Without `paho-mqtt` the server still starts and the monitor reports ERROR. Capabilities are honest about the write path: `read_only: false`, `mqtt_publish: true`, `remote_post: false`, `config_apply: false`, `admin_default_password` (boolean only), `host_power` (`available`, `reason`, `actions`; the loopback listener only) and a `config_patch` block (`enabled`, `topic`, `get_topic`, `ack_topic`, `settings_topic`, `qos`, `ttl_ms`, `ranges` from `rdf_node_commands.ranges_view()`, `gain_table_db`). `GET /api/mqtt` is the one MQTT status: broker, transport, `connection`, `last_error`, `node_id`, `root` (`sdr/v2/uav-01`) and the message counts of every subscribed RDF Node topic (`received`, `valid`, `invalid`, `cleared`, `last_received_at_ms`, `last_age_ms`, the same counts as `/api/mqtt/rdf-node`); it keeps `read_only: true, publish_enabled: false`, because the monitor never publishes on its own.
- The LAN view (`tools/lan_access.py` for the settings and request rules; `LanConsoleHandler`, `LanViewServer` and `LanAccessManager` in `ground_console.py`) is off by default. `lan_access` in `console.json` holds `enabled`, `port` (default 8788, 1024–65535, not the console port), `bind` (`0.0.0.0`, `::` or a literal non-loopback address of this host) and `allowed_clients` (IPv4/IPv6 addresses or networks, at most 32, none broader than /16 or /48, no `0.0.0.0/0`, `::/0` or loopback-only entry; an empty list admits nobody); an invalid saved block loads as the default. `GET /api/lan-access` (no admin, the Receiver read rule: this console's own pages only) returns `{config, status}`; `POST /api/lan-access` needs the same-origin loopback `Origin` and the admin cookie, refuses enabling while the default admin password is in use (409 `LAN_ADMIN_PASSWORD_DEFAULT`), saves, and opens, moves or closes the listener at once (a failed bind leaves it closed with `BIND_FAILED` and the errno name; on `EADDRNOTAVAIL` or `EADDRINUSE`, such as a literal LAN address the network brings up after a boot start, the bind is tried again after 5, 10, 20 and 40 s and then every 60 s while the setting stays enabled, `LAN_BIND_RETRY_DELAYS_S`, until a save or the console stop). Its codes (`LAN_ACCESS_INVALID`, `LAN_ACCESS_SAVE_FAILED`, `ADMIN_REQUIRED`, `ORIGIN_REJECTED`) and the LAN view's own go through `_send_lan_error`, outside the Kontrol code list. `/api/console-config` never shows `lan_access` and refuses it in a POST; a console-config save keeps the saved block. At start an enabled setting stays closed while the admin password is the default or admin login is disabled or unreadable (reason `ADMIN_PASSWORD_DEFAULT`, `ADMIN_DISABLED`), with a warning line; `/api/health` carries `lan_access {enabled, state, reason}` and the loopback capabilities `access: "local"` with the full status (`bind`, `port`, `address`, `detail`, `allowed_client_count`). The LAN listener admits on its accept thread (`LanViewServer.process_request()`): a client address outside `allowed_clients` gets a bare 403 there, logged at most once a minute per address, without a handler thread and without its request being read (`AnsweredSockets` keeps the socket at most 2 s to drop late request bytes, at most 64 such sockets); an allowed client gets a handler thread while fewer than 32 requests are open (`MAX_CONNECTIONS`; a bare 503 with `Retry-After: 1` otherwise, logged once a minute), and its request line and headers must arrive within 10 s in all (`REQUEST_DEADLINE_S`, through `request_reader()`). The handler then checks, in order: the method (only GET and HEAD, else 405 `LAN_READ_ONLY`); one Host (so no HTTP/0.9 request) that is an IP literal, this host's name or `<host name>.local` on the listener's port (any other `.local` name is refused, since another LAN host can answer mDNS for it), and no `Sec-Fetch-Site: cross-site` (403 `ORIGIN_REJECTED`); then the path: the built UI (`/`, `/index.html`, the favicons, `assets/`), `/api/health`, `/api/capabilities` (`access: "lan-view"`, `read_only: true`, `admin_enabled: false`, `config_patch.enabled: false`, `preferences_read_only: true`, no `host_power`), `/api/snapshot` (the configured Data Out only; a `base_url` query is ignored; `seen` takes part in the shared read like a loopback viewer; `refresh` and `fresh_settings` are ignored, so LAN clients never read Data Out more often than the saved interval), `/api/console-config`, `/api/mqtt`, `/api/mqtt/rdf-node`, `/api/preferences` (with `read_only: true` and only `LAN_VIEW_PREFERENCE_KEYS` of `tools/preferences_store.py`: the shell, Overview panels, basemap, overlay, polar view and GPS and Compass source, never the Receiver's `SDRSetting`, `ReceiverSweepSettings` and `sdr-web-bookmarks` or the spectrum dock's keys), `/api/branding`, `/api/tiles/...`, `/api/admin/status` (always false: the admin cookie is never read there) `GET /api/mirror/receiver` (below) and the Records reads: `GET` `/api/receiver/archive/{facets,calendar,timeline,items}`, `archive/scans/<id>/preview`, `archive/audio/<id>/download`, `archive/scans/<id>/download` and `/api/receiver/audio-segments/<id>/audio`, matched exactly with a record UUID (`lan_access.records_route()`), served by `LanConsoleHandler._lan_records_get()` under its own read rule (the LAN Host rule and `Sec-Fetch-Site` absent, `none` or `same-origin`) and limits (one list read per client, 50 rows a page, 4 downloads or playbacks per client, one scan ZIP for the LAN view apart from the groundstation's two, HEAD of a download 405, no stale-session recovery from a LAN read; see `CLAUDE.md`). Every other path is 403 `LAN_READ_ONLY`, `/receiver/`, every other `/api/receiver/*` route (settings, marker sets, raw scan routes, exports, delete, retention), `/api/mqtt/config-*` and `/api/lan-access` included. Answers carry the loopback listener's CSP and headers. `server_close()`, and so SIGTERM, closes it.
- The Receiver mirror (issue #15 phase 2, `docs/RECEIVER_MIRROR.md`, `tools/receiver_mirror.py`): the LAN view sees the groundstation's Receiver without a radio of its own. `POST /api/mirror/receiver` takes the latest state and spectrum frame only from the console's own page (same-origin loopback `Origin`, 403 `ORIGIN_REJECTED`), at most 8 KiB (413 `MIRROR_TOO_LARGE`), at most 12 posts in any second (429 `MIRROR_RATE_LIMITED`), only while the LAN view is open (409 `MIRROR_LAN_CLOSED`), with a strict schema (400 `MIRROR_INVALID`: unknown fields, missing fields, wrong types, out-of-range values, a frame of 16–512 u8 bins as base64 over a stated `db_min`..`db_max`). - The Kontrol command routes (`docs/MQTT_KONTRAK.md` section 9): `GET /api/mqtt/config-reported` (no admin, always 200: broker connection, the node session from RDF Node `state` with `sid`, `cfg`, health freshness and the `remote_*` capabilities, `base_rev` = `state.cfg`, the latest `settings/reported` with `matches_state_cfg`, its safe values with the server time each arrived, `value_received_at_ms`, only while the report's `rev` is `state.cfg`, and the latest `config.get` as `settings_request`), `POST /api/mqtt/config-patch` (body `{changes, base_rev, confirm: true}`, at most 4096 bytes; 202 with `command_id`, `topic`, `qos`, `base_rev`, `issued_ms`, `expires_ms`, `ttl_ms`, the normalized `changes`), `POST /api/mqtt/config-get` (body `{}`; 202 the same way) and `GET /api/mqtt/config-patch` / `GET /api/mqtt/config-patch/<command_id>` (command status, no admin; the bare path returns the latest `config.patch` so a reload can resume). The server builds the envelope (`tools/rdf_node_commands.py`: `v` 2, `id` `gc-` + 24 hex, `sid` and `boot` of the latest `state`, `issued_ms` on the server clock, `expires_ms` 15 s later, `base_rev`, `op`, and for a patch `changes` in the edge's field order) and checks it as the edge does before publishing. The fields are the edge's five safe fields (`center_frequency_hz` and `vfo0_frequency_hz` 24–1766 MHz in whole Hz, `vfo0_bandwidth_hz` 100 Hz–2.4 MHz whole, `gain_db` a value of the edge's gain table, `vfo0_squelch_db` −200..50 dB), and a centre change must carry `vfo0_frequency_hz` at the same frequency; refusals use the edge's own codes for the same rules (`FIELD_NOT_ALLOWED`, `VALUE_OUT_OF_RANGE`, `GAIN_NOT_IN_APPROVED_TABLE`, `CENTER_CHANGE_REQUIRES_VFO0_TARGET`, `MVP_CENTER_MUST_EQUAL_VFO0`). POST checks run in a fixed order and the first failure wins: Origin (403 `ORIGIN_REJECTED`), admin (401 `ADMIN_REQUIRED`), request shape, `confirm`, fields (400), monitor present, publish-capable and connected with every SUBACK (409 `MQTT_MONITOR_DISABLED`, 503 `MQTT_DEPENDENCY_MISSING` / `MQTT_NOT_CONNECTED`), a node session (409 `NODE_SESSION_UNAVAILABLE`), then for a patch fresh health (409 `NODE_NOT_FRESH`), `state.cfg` known and equal to the reviewed `base_rev` (409 `CONFIG_REVISION_UNKNOWN` / `CONFIG_REVISION_STALE` with `current_base_rev`) and no other patch in flight (409 `COMMAND_IN_FLIGHT`), for a get no other get waiting (409 `SETTINGS_REQUEST_PENDING`) and 1 s since the last (429 `CONFIG_GET_TOO_SOON`), then the publish (502 `MQTT_PUBLISH_FAILED`). Error bodies are `{ok: false, code, error, ...}`. `tools/config_command_tracker.py` keeps the last 32 commands on the server (`config.get` and `config.patch` share the bound, so it drops the oldest final ones and never one that is not final: quick gets never push out a patch that waits for its final ACK) and derives each state from what the monitor saw for that id (PUBACK, the edge's ACKs on `ack/config`, the `settings/reported` answer): `published`, `delivered`, `acknowledged` (`ACCEPTED`, `APPLYING`, `VERIFYING`), then the final `acked` (the edge's final ACK with its status, `result.error`, `reason`, `revision` and `proof`), `reported` (a `config.get` whose report came), `publish_failed`, `no_ack` (no ACK by expiry plus 5 s), `no_final_ack` (a progress ACK but no final one within 90 s) or `no_report` (a `config.get` applied without a report within 60 s); a late final ACK still upgrades the three timeout states, and nothing is ever resent. A monitor follows only the ids it published, so a Reconnect or an MQTT settings save hands the commands that are not final to the new monitor (`ConfigCommandTracker.hand_over()`, `MqttMonitor.adopt_rdf_node_commands()`), which then receives their ACKs and settings report. Correlation is server-side because the browser redacts payload keys ending in `id`. The old topics' `config_reported` revision is no longer read; the base revision is always the node's `state.cfg`.

It posts a patch only from the review step with `confirm: true` and the reviewed `base_rev` (Send also needs a connected monitor, the node session, `state.cfg` and fresh health), then polls the command status every 1 s until it is final, showing the edge's progress (`ACCEPTED`). `APPLIED` is the only success; `PERSISTED_UNVERIFIED`, `OUTCOME_UNKNOWN` and `no_final_ack` show in an info tone as neither success nor failure; `REJECTED`, `CONFLICT`, `EXPIRED`, `CANCELLED` and `FAILED` show the edge's `result.error` with a message; results read in operator words with the raw codes on their own line, and an exception code of the edge's settings helper (`OSERROR`, `FILENOTFOUNDERROR`, ..., `edgeHelperFault()`) names the helper missing or not approved on the RDF-SDR; a stale or unknown base revision (`CONFIG_REVISION_STALE`, `CONFIG_REVISION_UNKNOWN`), a newer `state.cfg` while reviewing and `CONFIG_REVISION_CONFLICT` send a `config.get`, read the values again and bring the same change back for review on the new revision (`rebaseOutcome()`), so one more Send confirms it; `NODE_NOT_FRESH` and `NODE_SESSION_UNAVAILABLE` keep the draft and read the values again; with `remote_config_patch` false Send needs an explicit second confirmation. Nothing is resent on its own. Fields (the gain as a select of the edge's gain table; typing the centre moves VFO0 along), units (MHz, kHz, dB on screen; Hz and dB on the wire), fallback ranges, the edge error messages (`EDGE_ERROR_KEYS`) and the hard-coded list of backend error codes are in `lib/configPatch.ts`.
- Kontrol's current values (form defaults and the review's "from") are the node's `settings/reported` first (only a report whose `rev` is `state.cfg`; the edge sends one only after a `config.get`; edge `8691ad0`, the installed release, only over a TLS link to the broker and otherwise answers `REJECTED TLS_REQUIRED_FOR_SETTINGS_REPORT`, while `35984d8` and later also answer over a plaintext link to the primary broker, `docs/MQTT_KONTRAK.md` 7a), then a fresh live Data Out `settings.fields` value (Data Out (fallback)) for what it does not carry, else "not reported"; the panel names the source. After a final command other than `publish_failed`, Kontrol reads the change back with `lib/configVerify.ts`: per sent field the sent value, the `settings/reported` value, counted only when the report arrived after the command's `issued_ms`, and the fresh Data Out value (`center_freq` in MHz, `uniform_gain`, `vfo_freq_0`, `vfo_bw_0`, `vfo_squelch_0`; only from a settings.json read at or after `issued_ms`, `settings.read_at_ms`, since the console reuses it for up to 30 s). `settings/reported` decides when it carries the field; Data Out only otherwise. A field is CONFIRMED within ±500 Hz (frequency), ±1 Hz (bandwidth) or ±0.05 dB, PENDING until 90 s after the final state (no wait when the ACK says the patch was not applied: `REJECTED`, `CONFLICT`, `EXPIRED`, `FAILED`, `CANCELLED`), then UNCHANGED, or NOT REPORTED when no source carries it. "Cek ulang" sends a `config.get` and re-reads config-reported and Data Out with settings.json (App's `refresh` with `freshSettings`, passed through `OverviewPage` as `onRefreshSnapshot`); Kontrol runs the same reads once when a command becomes final. A synthetic snapshot never counts.
- `doaGeometry.ts` generates geodesic bearing, lobe, guide, beam-sector, density-heat, range-ring, and −3 dB edge features, plus the −3 dB width and bearing/distance helpers. `overlayPalette.ts` holds the shared palette stops and MapLibre paint expressions. Signed dB normalization and projection distances are visual parameters, not physical RF conversions.
- `simulation.ts` creates a finite synthetic 360-bin snapshot with publication `BLOCKED` and no authority. `App.tsx` applies it only to Overview; health, diagnostics, runtime, and MQTT remain live, and so do the spectrum dock and Kontrol (follow-node ignores a synthetic snapshot).
- `sdr_doa_mqtt_monitor.py` (the console's one MQTT client; `rdf_node_view()` hands the RDF Node view to `telemetry_source.py`) and `rdf_node_mqtt_v2.py` (the RDF Node edge at `sdr/v2/<node>/`, its validator and store) share one paho connection that subscribes: transport `tcp` or `websockets` (path `mqtt_ws_path`, default `/mqtt`), a random `groundconsole…` client id (never the `uav-01-ground` id of the RDF Node's own `rdf-ground.service`), no TLS or credentials. `rdf_node_mqtt_v2.py` follows `docs/MQTT_KONTRAK.md`, the edge contract of RDF Node commit `8691ad0` (release `1.0.0-20261013194717`; later fields such as the PPP fields of `telemetry/health/detail` are optional): it subscribes to the 12 edge topics (`state`, `capabilities`, `availability`, `telemetry/health`, `telemetry/health/detail`, `telemetry/doa`, `telemetry/diagnostic/doa`, `telemetry/angular`, `telemetry/diagnostic/angular`, `settings/reported`, `ack/config`, `ack/operation`; `config/reported` is no longer one, so a retained leftover is never read), reads leniently (`docs/PRINSIP_DATA.md`, contract section 3): payloads over 8192 bytes, broken JSON, `NaN`, duplicate keys, another `v`, an empty `sid` and a missing core field are `INVALID` with their code, while numeric text, 0/1 booleans, seconds, missing optional fields, a wrong QoS or retain, an unknown ACK status and incomplete Angular evidence are accepted with `CODE:field` notes on the value and the topic entry, and health, DoA and Angular outside their window or without health are kept as `STALE` or `INCONSISTENT`; it gives each topic the status of its latest message: `LIVE` (DoA `ok=1` and Angular `flags=63` with health fresh for 8 s, `daq=1` and an advancing `q`), `UNVERIFIED` (DoA `ok=0`, trust-only Angular, both diagnostic topics; never LIVE), `FRESH`, `CONTEXT` (retained `state`, `capabilities`, `availability`), `STALE` (outside the source window: health 8 s, DoA 5 s, Angular 10 s, 1 s ahead), `INCONSISTENT`, `IGNORED` (no `state` yet, `q` not advancing, an unrequested `settings/reported`) or `INVALID` (with the field). A new `sid` in `state` drops the old session's data; revisions are metadata, except that DoA `ok=0` must carry `state.cfg`. Its node view holds accepted values only (session, health, detail, LIVE DoA and Angular, the RAW, diagnostic and trust-only ones apart, capabilities, availability, the last 32 ACKs without any `challenge`, and a `settings/reported` that answers a registered `config.get`, whose native text stays server side), and `session_view()`, `expect_settings_report()`, `settings_report()` (its `safe_settings` only while `matches_state_cfg`, the report's `rev` being `state.cfg`) and `ack()` (on the monitor: `rdf_node_session()`, `expect_rdf_node_settings_report()`, `rdf_node_settings_report()`, `rdf_node_ack()`) are what the Dashboard and Kontrol steps build on. `GET /api/mqtt/rdf-node` serves its `topics`, `topic_counts`, `invalid_counts` and `node`. Its only publish is `MqttMonitor.publish_rdf_node_command()`, called by the server for an admin-gated Kontrol command after `rdf_node_commands.validate_command()`: QoS 1, `retain=False`, `MessageExpiryInterval` equal to the 15 s TTL, and only while connected with every SUBACK in, so paho never queues a command for replay after a reconnect; a `config.get` registers the settings report it expects before the publish. PUBACKs arrive through `on_publish`; `wait_for_publish` is never called under the monitor lock. The monitor keeps, for the last 32 commands it published (dropping an answered one first, never a waiting patch before every `config.get`), the PUBACK and the edge's ACKs and settings report for that id (`rdf_node_command_observation()`, fed by the store's `on_accepted`) and serves the node session and settings for Kontrol (`rdf_node_control_view()`), outside the Message Monitor snapshot. Message Monitor has no topic-family switch. It shows the RDF Node view, which polls `GET /api/mqtt/rdf-node` every 2 s while the page is open (the counters, a Node card with one row per node view part with its status, age, reasons and fields, a DoA or Angular direction only while the part is LIVE or UNVERIFIED, an ACK card and the topic table with each status and refusal code), then a Connection card (broker, transport, topic root, publish mode). Configuration's MQTT card shows the message count and the last message's age from `/api/mqtt`.

## Development Commands

Install and validate the frontend from `frontend/`:

```sh
cd frontend
npm ci --ignore-scripts --no-audit --no-fund
npm run check       # TypeScript build/typecheck, not lint
npm test            # Vitest run
npm run build       # tsc -b && vite build; empties and rewrites frontend/dist, including dist/receiver

npm run dev         # Vite development server on 127.0.0.1
npm run preview     # Vite preview on 127.0.0.1
```

Run the production UI through the Python server from the repository root:

```sh
.venv/bin/python tools/ground_console.py --bind 127.0.0.1 --port 8787
# legacy embedded UI, when specifically needed
.venv/bin/python tools/ground_console.py --legacy-ui --bind 127.0.0.1 --port 8787
```

The default URL is `http://127.0.0.1:8787/`. Vite alone does not provide the `/api` backend. Never expose the Ground Console or Vite server on a non-loopback address; the only LAN exposure is the opt-in, read-only LAN view an admin enables in Configuration (`lan_access`), never a reverse proxy, `socat` or port-forward.

Release and packaging (Linux; details in `QUICKSTART.md` and `packaging/*/README.md`):

```sh
python3 tools/make_release.py                 # npm ci + build:all, then the console tarball, sdr-doa-docker and SHA256SUMS in dist/release
python3 tools/make_release.py --skip-build    # package the existing frontend/dist
docker compose up -d --build                  # console image from a regular clone (host network, volume /data)
sudo sh packaging/docker/sdr-doa-docker install --auto-update   # console from the GHCR image, daily update with rollback
sh packaging/console/install.sh --help        # native install: venv, systemd user service, sdr-doa-console
sdr-doa-console update --check                # native install: newest release of the same major; auto-update on|off|status
sudo sh packaging/ground-link/install.sh --dry-run   # T900 PPP link diag, watchdog and t900-link on the groundstation host
```

A GitHub Release comes from CI, not from a local build: bump `VERSION` on main together with the files that name it (every release: the `image:` tags of `docker-compose.yml` and `docker-compose.release.yml`, and a `## <V>` section in `CHANGELOG.md`, which becomes the release page's text; a new major also `DEFAULT_CHANNEL` in `packaging/docker/sdr-doa-docker`, `${SDR_DOA_IMAGE_TAG:-N}` in `docker-compose.ghcr.yml` and the channel text of the script, that compose file and the docs; the tests fail otherwise), then push the tag `v<VERSION>` (`git tag v3.2.0 && git push origin v3.2.0`) or run the Release workflow on main. `release.yml` tests the tree, builds the tarball with `make_release.py --with-wheels`, publishes `sdr-doa-ground-console-<V>-linux.tar.gz`, `sdr-doa-docker` and `SHA256SUMS` with that `CHANGELOG.md` section as the release notes, and then pushes `ghcr.io/sanadunt/sdr-doa-ground-console` (amd64, arm64) built from that tarball, tagged `<V>`; the channel tags `<MAJOR>.<MINOR>`, `<MAJOR>` and `latest` move to it only when no higher stable release they cover exists (a prerelease gets only `<V>`). Whoever can push a tag or write packages reaches every auto-updating host; `QUICKSTART.md` ("Rilis di GitHub") lists the GitHub settings that limit that.

Installs update without a GitHub login, because the repository, its release assets and (once set Public) the GHCR packages are public. Docker: `sdr-doa-docker update` pulls the channel tag (default the major), waits for the health check, puts the previous image back when the new one fails and records an image that failed its health check so the daily `sdr-doa-docker-update.timer` skips it; `--auto` also skips an image older than the running one. Native: `sdr-doa-console update` reads the latest release from the GitHub API, checks `SHA256SUMS` and `MANIFEST.sha256`, runs that release's `install.sh` with the recorded options and restores the previous program when `/api/health` does not report the new version; `sdr-doa-console-update.timer` runs it daily (`update --auto`). Both timers wait while `/api/health` reports `receiver_busy` (a Receiver recording or scan archive), at most 7 days. Neither timer crosses a major version: a host moves to a new major with `sdr-doa-docker install --channel N` or `sdr-doa-console update --allow-major` (`CHANGELOG.md`). See `CLAUDE.md` ("Settings persistence and Linux packaging", "CI and releases").

Every launch path (Docker entrypoint, systemd unit, `sdr-doa-console run`) passes `--bind 127.0.0.1` and one data directory: `--config-path DATA/console.json --branding-path DATA/branding.json --preferences-path DATA/preferences.json --data-dir DATA/receiver --tile-cache-dir DATA/tiles --env-file DATA/.env`, with DATA = `/data` in Docker or `~/.local/share/sdr-doa-ground-console` natively. Docker runs as uid 10001 with `network_mode: host`; never publish ports from a bridge network.

## Code Conventions & Common Patterns

- TypeScript is strict. Normalize external values from `unknown`, then apply finite/range checks. Represent unavailable, stale, conflict, and error states explicitly instead of coercing bad data into valid-looking values.
- UI text lives in `lib/i18n.ts` with English and Indonesian dictionaries; read it through `useI18n()`. Add every key to both dictionaries (`i18n.test.ts` enforces key and placeholder parity). Status codes such as `STALE` or `BLOCKED` stay untranslated. The language choice is stored in `localStorage` under `sdr-console-lang` and synced to the console like the other preferences.
- Use pure helpers for contracts and transformations. Keep API validation in `api.ts`, telemetry readiness/gate logic in `lib/telemetry.ts`, GPS selection in `lib/map.ts`, angle conversion in `lib/polar.ts`, and GeoJSON math in `lib/doaGeometry.ts`.
- React state is lifted into `App.tsx` and passed through callback props. Effects must clean up timers, abort controllers, observers, MapLibre resources, Plotly instances, and listeners because the app mounts under `StrictMode`.
- Preserve latest-request-wins behavior and local freshness expiry. Do not recreate map/plot layout or camera state for ordinary data updates. Use `localStorage` only for operator preferences (theme, language, basemap style, overlay settings, GPS/Compass source choice, Overview panels and node-card collapse, polar view, listen mode, follow-node, the spectrum dock's mode, scan dB Auto choice and last known RX dB scale), with validation on restore and every access in try/catch. Write them through `writePreference()` or `preferenceStorage()` so they reach `/api/preferences`; a new key must be added to `PREFERENCE_KEYS` in both `lib/preferenceStore.ts` and `tools/preferences_store.py` (the contract test compares them). Never put secrets, credentials or live data in a preference.
- Components use `PascalCase`; functions, variables, and hooks use `camelCase`; constants use `UPPER_SNAKE_CASE`; Python modules/functions use `snake_case`; Python tests use `test_*` entry points.
- Python paths are intentionally bounded and defensive: allowlisted URLs, no redirects, finite timeouts, body limits, redaction, atomic local writes, and explicit loopback checks. MQTT payloads are schema-validated, size-bounded, and latest-value-wins per stream.
- Keep live, fixture, and synthetic data separate. Simulation must remain visibly labeled `SIMULATION` and must not affect health, diagnostics, MQTT, publication authority, or Raspberry state.
- Preserve the freshness gate, publication gate, redaction, CSP, timeout/abort handling, the monitor's rule that it never publishes on its own, and the dry-run boundary of the Configuration form. The one remote write path is Kontrol's RDF Node commands (`POST /api/mqtt/config-patch` to `cmd/config/patch`, and `POST /api/mqtt/config-get` to `cmd/config/get`, which changes nothing on the node). Keep all of their rules: loopback bind only; a port-exact same-origin loopback `Origin` header (no header or another origin gives 403 before the body is read); the admin cookie; for a patch `confirm: true` sent only after the UI review step, the edge's fields and rules checked on the server (`rdf_node_commands.py`), fresh node health, and the reviewed `base_rev` equal to the node's `state.cfg`; the envelope built on the server, never in the browser; QoS 1, never retained, 15 s TTL (at most 30 s, also as `MessageExpiryInterval`); at most one non-final patch and one waiting `config.get` at a time; no automatic resend; publish only while the monitor is connected with its subscriptions acknowledged; no MQTT in the browser and no MQTT credentials in the console. `POST /api/admin/login`, `/api/admin/logout`, `/api/console-config`, `/api/lan-access`, `/api/mqtt/connect` and `PUT`/`POST /api/preferences` also require that same-origin loopback `Origin` (403 `ORIGIN_REJECTED`), because they control the admin session, the LAN listener and the MQTT monitor that carries the patch; failed logins from other origins never reach the login throttle. The LAN view answers no write at all and never reads the admin cookie. The console itself never publishes the bearing. The host power request keeps its rules too (`POST /api/host/power`, `tools/host_power.py`): the same-origin loopback `Origin` before the body is read, a strict body of at most 256 bytes with `confirm: true`, one word written atomically into the request directory and never a command run by the console, no route, capability or button on the LAN view, and codes sent through `_send_host_power_error`, outside the Kontrol code list. Do not add another remote write path or another write to the host, and do not expose secrets to `VITE_*` or browser state.
- Styles load in `main.tsx` as `styles.css`, then `console-design.css`, then `polar-layout.css`, then `overview-dashboard.css` (the `.ov-*` dashboard classes, `--ov-dock-h`, `--ov-gap`), then `page-kit.css` (the `.pg-*` page kit: `--pg-*` tokens, page bar, 12-column grid with spans 3/4/5/6/7/8/12 that become 6 or 12 below 1280 px and one column below 1024 px, cards, stat tiles, key/value grids, tables that stack into cards at 600 px and below, fields, switches, notices; console tokens only, no literal colours). Later files override earlier declarations. Non-dashboard pages carry no footer, eyebrow or description: their H1 is the page bar's title, visually hidden above 600 px where the top bar names the page, and shown with the read age at 600 px and below, where the top-bar title is hidden. Like the Dashboard, their cards carry labels, values, chips, errors, warnings and prompts that need an action, and a result says what happened in a few words ("Monitor restarted."); a tooltip names only a current cause, such as the stalled or regressed counters on System Health's progress value, never what a state or a button means. Dashboard touch targets are at least 44 px. At 1023 px or less the dashboard stacks in normal flow (map, HUD, Lapisan, node card, Kontrol, Polar, Spektrum) and the page scrolls; at 600 px or less it uses a 16 px side gutter. Check responsive and reduced-motion behavior when changing UI.

## Runtime/Tooling Preferences

- Use npm from `frontend/` with the committed lockfile. Project docs recommend Node 22.12+ within a supported Node 22 LTS; Vite/plugin engine ranges also accept newer supported Node versions. No root package manager, `.nvmrc`, or npm version is pinned.
- Use the project `.venv` for Python commands, Python 3.9 or newer (the console imports `zoneinfo` through the Receiver store). The Python tools are mostly standard-library code. `paho-mqtt==2.1.0` is needed for the MQTT monitor and its tests; without it the console starts with the monitor in ERROR. On Windows, `tzdata` only makes the local times in Receiver ZIP file names follow the browser's zone; the Records calendar and time ranges use the browser's own day bounds.
- There is no Python dependency manifest for development (only `packaging/console/requirements.txt` for installs), and no formatter, linter, or coverage configuration. GitHub Actions runs the verification sequence (`.github/workflows/ci.yml`) and publishes releases (`release.yml`); see `CLAUDE.md`, "CI and releases". Docker and Compose files exist for Linux deployment only. `npm run check` is the defined static check; there is no `npm run lint`.
- Build `frontend/dist` with `npm run build:all` before full static-serving QA. The static regression suite skips build-dependent checks when `frontend/dist/index.html` is absent, and fails its Receiver checks when `frontend/dist` exists and `vendor/BrowSDR` is checked out but `frontend/dist/receiver` is missing.
- Keep credentials in the process environment or the env file (`--env-file`, default the ignored root `.env`). `SDR_DOA_ADMIN_PASSWORD` is Python-only; never rename it to a `VITE_` variable or embed it in the frontend bundle. The process environment wins over the env file. When the variable is absent from both, the default password `123456` applies: the server prints a startup warning, capabilities report `admin_default_password: true` (never the password), and Kontrol shows a warning. An explicitly empty value (`SDR_DOA_ADMIN_PASSWORD=`) disables admin login (503 `ADMIN_DISABLED`). A `.env` that exists but cannot be read or decoded also disables login instead of falling back to the default. After 5 failed logins within 60 s, every login, the correct one included, gets 429 `ADMIN_LOGIN_THROTTLED` for 30 s (counted for the whole server). The admin session is an HttpOnly, SameSite=Strict cookie with a 30 min TTL; it unlocks branding and Kontrol. Password changes need a console restart.
- Local console defaults are loopback bind `127.0.0.1`, port `8787`, Data Out `http://doasdr.local:8081` (hosts from the saved `data_out_hosts` list, default `doasdr.local`, `192.168.100.100`, `127.0.0.1`, `localhost`; port 8081 only), and MQTT `10.90.0.1:9001` over WebSocket. The MQTT host may be any IPv4/IPv6 literal or `localhost` (no DNS names); the console opens an outbound MQTT connection there (it subscribes, and publishes only Kontrol's admin-gated commands) while its own HTTP bind stays loopback. A Kontrol send works only through a broker that accepts this anonymous, non-TLS client and lets it publish to `sdr/v2/uav-01/cmd/config/patch` and `cmd/config/get`; edge `35984d8` and later answer `config.get` with `settings/reported` over a plaintext link to the primary broker too, while edge `8691ad0` (the installed release) answers only over TLS, so until the RDF-SDR is updated the values come from Data Out (fallback) unless that broker has a TLS listener for the RDF-SDR (`docs/MQTT_KONTRAK.md` 7a). Staging broker files are not production security configurations.
