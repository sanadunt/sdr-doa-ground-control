## Receiver (embedded BrowSDR)

`AGENTS.md` lists the second route (`#/receiver`, `ReceiverPage.tsx`, key `2`); the details are here. It iframes a separately built BrowSDR sub-app served same-origin at `/receiver/`.

- Display names: the UI shows the HackRF as RadioSpectrum and the Raspberry node as RDF-SDR (console i18n, the overlay's own strings, and `radioDisplayText()` in the overlay's `i18n.ts`, which `tm()` and the board, picker and USB product names go through). Code identifiers, API fields, MQTT topics and the WebUSB filters keep the technical names; the browser's own USB chooser still shows the USB product name.
- Source is the `vendor/BrowSDR` git submodule, pinned by `BROWSDR_REVISION` in `tools/build_browsdr_receiver.py`. Fetch it with `git submodule update --init --recursive`.
- Do not edit `vendor/BrowSDR`. Local changes live in `tools/browsdr_receiver_overlay/src/` and are applied at build time: the builder copies the submodule to a temp dir, overlays those files, patches anchors with `_replace_once` (it fails if an anchor is missing or appears more than once), runs `npm ci` and `npm run build --base=/receiver/` with npm resolved through `shutil.which` (`npm.cmd` on Windows), and writes `frontend/dist/receiver`. If you bump the pin, also bump `BROWSDR_OVERLAY_BASE_REVISION` and re-check every anchor.
- Build order: `npm run build` empties `frontend/dist`, including `dist/receiver`. Use `cd frontend && npm run build:all`, or run `.venv/bin/python tools/build_browsdr_receiver.py` after every `npm run build`. Without the Receiver build, `/receiver/` returns a 404 page with these steps, and the static suite fails its Receiver checks when `vendor/BrowSDR` is checked out.
- Look: the frame cannot read the console's CSS variables, so `frontend/src/receiver-embedded-theme.css` repeats the `console-design.css` colours (both themes) under BrowSDR's variable names, and the builder appends it to the Receiver's `style.css`. The overlay `style.css` reads only those tokens (its last section is the console skin: header row with the workspace tabs, 44 px outline buttons, pill chips). Change both copies; `tools/test_receiver_theme_tokens.mjs` compares them. Canvas colours are patched by the builder. The Listener's WebGL waterfall (vendor `utils.ts`, three builder anchors) is transparent where it has no data yet and outside the zoomed band, so that part shows the `#waterfall` background `--canvas-bg` (black dark, `#fafbf9` light, the trace's own background); rows with data keep the colour map.
- Lifetime: the iframe mounts lazily, on the first `#/receiver` visit or the first Mulai/Dengar click in the Dashboard Spektrum dock, never at console load, because mounting runs `autoConnectAuthorizedHackRF` and claims the radio. In the LAN view (`access: "lan-view"`) it never mounts at all: the radio is on the groundstation's USB, and the LAN listener refuses `/receiver/` and `/api/receiver/*`; the LAN view shows the Receiver mirror instead (below). After that it stays mounted (hidden) across route changes, so RX, scans and recordings keep running until the console page reloads. Never move or key that section: it would reload the frame and stop RX. Shortcuts 1–9 and R are forwarded from the frame except while typing in a field there (`isTextEntryTarget()`; digits also stay inside a container marked `data-no-page-shortcuts`, such as the basemap radio menu); the console maps digits through `ROUTES` (`lib/routes.ts`), so the frame needs no change when the menu order changes. Theme and language arrive as `?theme=&lang=` and later through a `console-language-change` event, without reloading the frame. When the route becomes `receiver` again, `ReceiverPage` dispatches `console-theme-change` on the frame window, which makes the Receiver resize its canvases (they are 0×0 while hidden).
- Dashboard bridge (Overview Spektrum dock ↔ frame), `window.postMessage` with envelope `{ch: "sdr-console-receiver", v: 1, type, ...}`:
  - Senders are checked: the console takes only `event.origin === location.origin` from the frame's `contentWindow`; the frame installs the bridge only under a same-origin parent and takes only `window.parent`. Anything else is ignored.
  - Frame to console: `receiver:hello`, `receiver:status` (debounced 100 ms, except that a change of `running`, `connected`, `busy`, `error`, `recording` or the scan phase is sent at once, at most every 20 ms; 2 s heartbeat; `running` stays true through the RX restart of a new sample rate or FFT size (`_rxRestarting`), so follow-node, which retunes once when RX starts, sees no start; `_rxRestarting` is no Vue state, so while it alone reports a stopped RX as running the bridge looks again every `RADIO_POLL_MS` (50 ms), and a restart that fails shows as stopped at once), `receiver:spectrum` (2 MHz crop around the RX centre, 512 max-hold bins, at most 10 fps, transferred `Float32Array`, only while a subscriber wants frames and the page is visible: the dock while mounted, the Receiver mirror publisher while the LAN view is open; `subscribe(options, owner)` keeps one claim per owner, `dock` or `mirror`, and `mergeSubscriptions()` posts one `console:subscribe` with frames while any owner wants them, the most bins, the highest rate and the dock's span first; `centerHz` is the frequency the radio was tuned to when the worker took the frame, not the Receiver's centre, which moves before its debounced `setFrequency` reaches the radio: the overlay `worker/spectrum-tuning.ts` stamps each frame in device Hz, the bridge adds the Freq Shift, and a frame taken while a retune is under way or among the first `SPECTRUM_SETTLE_FRAMES` (3) after it is not sent), `receiver:sweep` (the running wide scan, below), `receiver:result`, `receiver:markers` (the Receiver's marker list, below). Console to frame: `console:hello|subscribe|start|stop|tune|vfo|listen|display|gains|radio|sweep-start|sweep-stop|sweep-config|sweep-display|marker-add|marker-remove`, each command with an id. Commands queue (16) until hello; `start`, `radio`, `sweep-start` and `sweep-stop` time out after 20 s (`LONG_COMMAND_TYPES`), the rest after 8 s (`TIMEOUT`); no hello within 8 s of load shows `NO BRIDGE`.
  - Frequencies are integer Hz of the displayed frequency, Freq Shift included (the dock shows `UPCONVERTER` when it is not 0). RX tuning stays inside `TUNE_LIMITS` (1 MHz–6 GHz); `SWEEP_LIMITS` (1–7250 MHz, device Hz without the shift) is the range for wide scans, and `MARKER_LIMITS` uses the same range for markers. The frame never calls `connect()`, `validateAndApplyVfoFreq`, `confirm()`, `saveMarkerSet`, `deleteMarkerSet`, `selectMarkerSet` or `requestWorkspace` (their dialogs would be invisible), changes the sample rate only through `console:radio` (below), and keeps VFO 1 muted on a start without listen (`initialVfoEnabled()`).
  - `SWEEP_BUSY` follows one rule (header of `console-bridge.ts`): during a scan listen every radio command is refused, `sweep-start`, `sweep-stop` and `sweep-config` included; during a wide scan `start`, `stop`, `listen` and `radio` are refused, while `tune`, `vfo` and `gains` only change the stopped Listener's settings, with no backend call (RX uses them when it starts again; a scan start that has not stopped RX yet refuses them too); the scan is started and stopped only by `sweep-start` and `sweep-stop` (`sweep-start` answers `OK` while a scan already runs); `sweep-config` is refused while a scan starts, runs or stops (read-only, as on the Receiver page); `display`, `sweep-display` and marker commands are never refused because of a scan.
  - Tune attribution: every console write of the centre or the active VFO (`tune`, `vfo` with a frequency, including its re-centre, `start` with frequencies, and the re-centre of `radio`) goes through `writeTuning()` in `console-bridge.ts`, which stamps it with the command id; any other change is the Receiver page's. `receiver:status` carries `tune: {rev, by: 'console'|'receiver', id, receiverRev}` (`rev` counts changes of the centre, the active VFO index or that VFO's frequency; `receiverRev` is the last rev not written by a command), and the results of `tune`, `vfo`, `start` and `radio` carry `tune` with `centerHz` and `vfoHz`, also when refused. The console keeps the highest rev as `BridgeState.tune` (`TuneView`). `watchReceiverTuning()` (`lib/receiverSync.ts`, one effect in `App.tsx`) turns "Ikuti frekuensi node" off when `receiverRev` rises after the first stamp of a frame, also while the dock is not mounted, and copies the Receiver's mode into the stored listen mode; both go through the page-wide stores in `lib/listenPrefs.ts` and it never sends a command.
  - RX dB scale: the Dengar tab has a "dB scale"/"Skala dB" panel (Auto|Manual, minimum and maximum in dBFS; overlay `listener-display.ts`). Auto fits the visible part of the spectrum (noise floor − 5 dB to peak + 5 dB, at least 20 dB, smoothed, at most every 100 ms) and stays outside Vue state; Manual draws `display.minDB`..`maxDB`. `display.auto`, `minDB` and `maxDB` are saved in `SDRSetting` (older saves load as Auto). The builder patches the Listener's `canvas.ts` (trace and waterfall engine range) through four anchors. Manual limits are `DISPLAY_DB_LIMITS` (−160..60 dB, at least 5 dB apart, `clampDisplayRange()` in both protocol copies). `receiver:status` carries `display: {auto, minDb, maxDb}` and `console:display {auto, minDb?, maxDb?}` sets it. The dock mirrors it in the Atur column; `watchReceiverDisplay()` (`lib/receiverSync.ts`, one effect in `App.tsx`) copies every newer Receiver value into `spectrumDockStore` (`lib/spectrumDockSettings.ts`, preference `sdr-console-spectrum-dock-v1`) and sends only a dock change, marked pending until the frame answers; a change made before the frame is mounted is sent after its hello, and the dock draws with the last known value until then.
  - RX radio settings (the Listener's sample rate, LNA, VGA and RF amp, saved in `SDRSetting`): `console:gains {lnaDb?, vgaDb?, amp?}` (at least one) writes `app.gains`, and the Receiver's gains watcher applies it live, without a restart. Values are checked against the connected device's `gainControls` (before a connect against `GAIN_LIMITS`: LNA 0–40 dB step 8, VGA 0–62 dB step 2; the amp is the control whose name starts with `Amp`); one bad value refuses the whole command (`OUT_OF_RANGE`). `console:radio {sampleRateHz, confirmRecording?}` is the only way the frame changes the sample rate, and replaces the old rule that it never did (the reasons stay: no surprise restart, no invisible dialog, no silently lost VFO). It runs in the lifecycle queue after any start or stop; the rate must be in `SAMPLE_RATES_HZ` (2, 4, 5, 8, 10, 16, 20 MSPS) and in the device's list (`OUT_OF_RANGE`); any scan answers `SWEEP_BUSY`; a running RX with an armed recording needs `confirmRecording`, which the dock sends only after a `window.confirm` in the console page (`RECORDING_ACTIVE` otherwise); an active VFO outside ±rate/2 of the centre is re-centred through `writeTuning()` and raw VFOs take the rate as bandwidth. The Receiver's `[sampleRate, fftSize]` watcher restarts a running RX as the Listener select does (an armed recording continues in a new segment); the answer waits until `_rxRestarting` is clear, RX runs and the Listener has drawn a frame of the new stream, and for a VFO that was audible until the restarted stream has created its AudioContext (`startStream` draws frames before it sets up the VFOs; at most `RADIO_RESTART_WAIT_MS`, 10 s), then reports `CONNECT_FAILED` when RX did not come back and `AUDIO_BLOCKED` when the VFO was audible before and the new AudioContext stays suspended. Both commands refuse a remote session with `NOT_READY` (the embedded build has none). `receiver:status` carries `sampleRatesHz` (the device's list, `[]` before a connect) next to `sampleRateHz` and `gains`. The dock's Atur column shows them as Sample rate, LNA, VGA and +14 dB (disabled with `—` until the frame answers; Atur never mounts it), holds a pick until the next status (`lib/radioSettings.ts`), shows `…` while a rate change restarts RX, keeps follow-node from retuning meanwhile, and adds the rate and the amp to the info line. A change on the Receiver page shows in the dock with the next status (about 100 ms).
  - Wide scan (the dock's Spektrum mode): `console:sweep-start {mock, confirmRecording?}` and `console:sweep-stop {resumeRx}` run in the lifecycle queue. A start uses the Receiver's own range and settings (`sweep.startMHz`/`endMHz`, saved in `ReceiverSweepSettings`): a connected RadioSpectrum scans with its hardware sweep (`SWEEP_UNSUPPORTED` when it has none), without one a mock start runs the simulated scan (the Mock SDR has no sweep, `MOCK_UNAVAILABLE` without `?mock=1`) and a real start connects through the same `connectForStart` path as `console:start` (`NEEDS_PAIRING`, `NEEDS_DEVICE_CHOICE`; RX started by that connect stays muted). It never calls `connect()`, `requestWorkspace` or `selectWorkspace`; it sets `activeWorkspace` to `spectrum` itself once the scan runs, and sets `returnToRx` to whether RX ran before the command, so a Receiver-page Stop resumes only RX the operator had. A scan stops RX, which ends an armed recording, so over a running RX with a recording it needs `confirmRecording` (`RECORDING_ACTIVE` otherwise; the dock asks with `window.confirm` in the console page). A start the Receiver refuses or that fails answers `SWEEP_FAILED` with the Receiver's notice, also when it repeats the previous one (the dock shows it after its own message); a start stopped on the way, such as by a Receiver-page Stop, answers `OK`. Either way the Receiver resumes the RX the scan stopped, and VFO 1 then plays or stays muted as before (`initialVfoEnabled()` returns its earlier state while the command runs; audio that played is resumed). `sweep-stop` waits for a start or a stop already under way (`SWEEP_STOP_WAIT_MS`, 15 s), so a following `console:start` finds the radio free. `console:sweep-config {startHz?, stopHz?, fftSize?, lnaDb?, vgaDb?, amp?}` (displayed Hz, at least one field) writes the scan settings only while no scan runs and no `sweep-start` waits; ranges are checked by `inSweepRange()` (device range `SWEEP_LIMITS` after removing the shift, at least `SWEEP_SPAN_LIMITS.minSpanHz` 1 MHz, at most `maxBins` 500 000 bins at 20 MSPS / fftSize: 1.22 GHz at 8192, 2.44 GHz at 4096), gains against `GAIN_LIMITS`, and one bad value refuses the whole command. `console:sweep-display {minDb, maxDb}` sets the Receiver's Graph min./max. (`DISPLAY_DB_LIMITS`), which the overlay `settings.ts` now saves with the scan settings; those fields, like the Dengar dB fields, have `step="any"`, so a 0.1 dB limit from the dock is a valid value there. `receiver:status` carries `sweep: {phase: idle|starting|active|stopping, source, startHz, stopHz (displayed), fftSize, resolutionHz, lnaDb, vgaDb, amp, displayMinDb, displayMaxDb, view}` with no progress counters. A hook in the overlay `sweep.ts` (the scan frame callback, outside every builder anchor) calls the bridge's `sweepFrame()`, which sends `receiver:sweep {seq, tMs, startHz, stopHz, resolutionHz, sweepCount, view, binCount, bins}`: the trace the Receiver shows (`sweep.view`), max-hold downsampled to the subscribed bins (`decimateMaxHold`), shifted to displayed Hz, at most the subscribed fps, a transferred copy, only while a scan runs and the dock (or the mirror publisher) subscribes; it shares `seq` with `receiver:spectrum`.
  - In the dock, an RX|Spektrum switch after the chip picks what Mulai starts; the dock shows the mode that runs (`dockMode()`), so a scan started on the Receiver page shows as Spektrum with live frames (chip `SCAN`; `…` while it starts or stops; `SCAN OFF` when stopped) and `BUSY` remains only for a scan listen. `DockView` has `rxRunning` (Dengar, follow-node) and `live` (the trace is drawn live: RX in RX mode, a running scan in Spektrum mode). In Spektrum mode Mulai/Berhenti start and stop the scan (`resumeRx: false`), a click or arrow key (step span/200, at least 10 kHz) sets the RX centre and VFO for the next RX at the strongest bin within two of the click and turns follow-node off, while the scan keeps running; Dengar stops the scan and starts RX listening; switching to RX while a scan runs stops it and starts RX, switching to Spektrum while RX runs starts the scan (asking first about a recording). `SIM` shows only while a simulated scan starts or runs. Axis ticks and readouts use the decimals the tick step and the bin width need; a stopped scan set to another range hides its old waterfall and peak. The Atur column in Spektrum mode shows the scan's dB scale (Auto is the dock's own; Manual is the Receiver's Graph min./max., seeded from `status.sweep` and sent only when a limit is typed), the range (Awal/Akhir MHz, "Pusatkan ke RX" centres the span on the RX centre), Resolusi (4.88 or 2.44 kHz; one the range does not fit is disabled) and the scan's own LNA, VGA and +14 dB, all disabled and tagged "Terkunci selama pindai" while a scan runs (`lib/sweepSettings.ts`). Before the frame is mounted the dock reads `ReceiverSweepSettings` (and the shift from `SDRSetting`) for the range and rows (`lib/receiverSavedSweep.ts`). `spectrumDockStore` also keeps the stored `mode` and `sweepAuto`.
  - Markers: the one store is the Receiver's "Penanda spektrum" list (`records.markers`, device Hz, with ids), saved to SQLite through `/api/receiver/marker-sets` only while a marker set is selected on the Receiver page; without one the list lives in the frame until the page reloads, as on the Receiver page. `receiver:markers {rev, setId, setName, frequencyShiftHz, markers: [{id, frequencyHz, powerDb, label}], total, truncated}` sends it in displayed Hz on install, with every hello and on every change of the list, the selected set or the Freq Shift (one key-getter watcher, `markersKey()`; each change counts one `rev`), at once after a quiet `MARKERS_THROTTLE_MS` (100 ms) and then at most that often, never in the heartbeat. It carries at most `MARKER_LIMITS.maxSent` (512) markers inside `MARKER_LIMITS`, nearest the RX centre or the middle of a running scan (re-sent when that moves while the list is longer), in frequency order; a missing label goes as `M<position in the list>`, as the Receiver's canvas names it, and an id outside `COMMAND_ID_PATTERN` as `null`. `console:marker-add {frequencyHz}` and `console:marker-remove {markerId}` run on their own queue (`MAX_QUEUED_MARKER_COMMANDS` 16, beyond that `NOT_READY`), never behind a start, and only through `addReceiverMarker`/`removeReceiverMarker` (overlay `records.ts`, which now return `{id, saved}` and `{removed, saved}`; `saveMarkerSet` returns whether it saved), which save only to the selected set, so the name-conflict `confirm()` of `saveMarkerSet` is never reached. A displayed frequency outside `MARKER_LIMITS` after removing the shift is `OUT_OF_RANGE`, a full list (`maxTotal`, 10 000, the record store's set limit) `MARKER_LIMIT`, an unknown id `MARKER_NOT_FOUND`, and a failed save to the set `MARKER_SAVE_FAILED` with the Receiver's text (the marker stays added or removed). The console sends no power: while a wide scan runs the frame measures it from the scan's own frame (`sweepPowerAt()` in the overlay `sweep.ts`, the code a click on the Spektrum canvas uses); otherwise it is `null`, since the dock's RX trace is dBFS on another scale. The add result carries `markerId`, and the frame posts the `receiver:markers` that shows a change before its result. The console keeps the newest list as `BridgeState.markers` (reset on attach and detach); it changes only when someone marks, so it is bridge state like the status, read through `useSyncExternalStore`, while frames still never are. The Listener (Dengar tab) also draws the markers in its visible span: overlay `listener-markers.ts`, called from the vendor `drawSpectrum` through a builder anchor in `canvas.ts` after the VFO highlights, with the Spektrum canvas's labels and colours, labels under the VFO labels; a watcher in the overlay `main.ts` rebuilds the shifted list and redraws a stopped Listener. On both canvases `placeMarkerLabels()` (overlay `sweep-marker-renderer.ts`) keeps labels from overlapping: from left to right a label whose place is taken moves to the next free row (down on the Dengar trace; up from just above the marker's power on the Spektrum canvas, down only where the plot top stops it) and is left out after `MARKER_LABEL_MAX_ROWS` (4) rows, while its line stays. ## Settings persistence and Linux packaging

- Everything saved lives on the console host, in files named by flags: `--config-path` (`console.json`: Data Out URL and host list, MQTT, refresh interval, the `lan_access` block), `--branding-path`, `--preferences-path` (`preferences.json`, the browser UI preferences), `--data-dir` (Receiver records), `--tile-cache-dir` (basemap tiles, disposable; `--tile-cache-max-mb`, default 512) and `--env-file` (`SDR_DOA_ADMIN_PASSWORD`, `SDR_DOA_SEED_*`; the process environment wins). Running from the repo without flags uses `~/.config/sdr-doa-ground-console/`, `~/.cache/sdr-doa-ground-console/tiles` and the repo `.env`. Installs use one data directory: `/data` in Docker, `~/.local/share/sdr-doa-ground-console` natively.
- First start only: when `--config-path` does not exist, the console writes it from `SDR_DOA_SEED_DATA_OUT_HOSTS`, `_BASE_URL`, `_MQTT_HOST`, `_MQTT_PORT`, `_MQTT_TRANSPORT`, `_MQTT_WS_PATH`, `_REFRESH_SECONDS` (invalid or empty values ignored with a warning). `_DATA_OUT_HOSTS` is comma separated and replaces the default host list; `_BASE_URL` is checked against the list that applies, and a host list that would leave the Data Out URL's host out is ignored with a warning (`install.sh --data-out-hosts` writes it to `seed.env`). `--base-url`/`--mqtt-*` override saved settings for one run and are never saved (`GroundConsoleServer` keeps the saved copy apart, and every save, `/api/console-config` and `/api/lan-access` alike, writes only the fields it changes, `_saved_copy_locked()`; a host list without the saved URL's host saves the URL in use), so the systemd unit, the launcher and the Docker entrypoint must not pass them; a typed `--base-url` must use a host of the saved list (on a first start the one just seeded), else `main()` exits naming the hosts and the port.
- Data Out hosts: `console.json` `data_out_hosts` (default `doasdr.local`, `192.168.100.100`, `127.0.0.1`, `localhost`; 1 to 16 hosts; port 8081 only) is the one list every Data Out check uses: `GroundConsoleServer`, `POST /api/console-config` (same-origin loopback `Origin`, like `base_url`), `/api/snapshot`'s `base_url`, the seed, `--base-url` and `collect(allowed_hosts=...)`. A host is a DNS name (RFC 1123 labels, lowercased, one trailing dot removed) or an IPv4/IPv6 address (IPv6 compressed, brackets allowed); no wildcard, scheme, port, path, userinfo, zone id, IPv4-mapped (`::ffff:0:0/96`, in any notation; list the IPv4 address, since some Python releases save the mapped form as a dotted quad that neither side reads back) or unspecified address. `normalize_data_out_host()`/`data_out_url_host()` in `sdr_doa_collector.py` and `lib/dataOutHosts.ts` apply the same rules, pinned by `tools/fixtures/data_out_hosts.json` (both test suites run it). Refusals are 400 `{ok:false, code, error, data_out_hosts, port}` with `DATA_OUT_URL_NOT_ALLOWED` (the URL's host is not in the list, or the URL is not `http://HOST[:8081][/]`), `DATA_OUT_HOST_IN_USE` (the list drops the host of an unchanged URL), `DATA_OUT_HOST_INVALID`, `DATA_OUT_HOSTS_EMPTY` or `DATA_OUT_HOSTS_TOO_MANY`, sent through `_send_data_out_error` so the Kontrol code contract never counts them. Configuration → Connection & refresh edits the list as pills (the URL field's host cannot be removed), Enter in the new-host field adds instead of saving, and one Save sends the URL and the list through the verified `updateConsoleConfig` path.
- `.local` Data Out hosts: the python slim image has no nss-mdns, so `fetch_resource` asks `tools/mdns_resolver.py` (stdlib only, the console passes `server.mdns_resolver`; the collector itself never imports it) only for a `.local` host, only after the system resolver failed, and only for a direct request (an environment proxy that takes the request resolves the name itself). One A question with the QU bit to 224.0.0.251:5353 from an ephemeral port (a legacy one-shot query, answered by unicast with the query ID echoed), sent once on every interface that is up, running, multicast-capable, not loopback and has an IPv4 address (`IP_MULTICAST_IF` per address, at most 32, read with Linux ioctls in `multicast_interface_addresses()`), as avahi does, because a plain `sendto` leaves only through the routing table's choice and fails with ENETUNREACH on a LAN without a default route; when no interface qualifies or takes the packet (or off Linux) it is sent once through the routing table; at most 1 s and never past the read's budget; answers parsed strictly (backward-only compression pointers, at most 16 jumps, the asked name only, class IN A, TTL above 0, no loopback, unspecified, multicast or reserved address, only from the port the query went to). Cache: the TTL clamped to 5..60 s, a failure kept 5 s, 64 names; while an address is cached the request connects there at once. The URL and the `Host` header keep the name and every fetch rule stays. `collection.host_resolution` is `{host, method: literal|system|mdns|proxy|null, address}` (`proxy`: an environment proxy took the request, `address` null because the peer is the proxy); System Health's Data Out card shows `mDNS <address>` or the address, and nothing for `literal` or `proxy`. When mDNS fails too, the error is `<host> could not be resolved (system and mDNS); use an IP address`.

- T900 PPP link of the groundstation: `packaging/ground-link/` holds host tools that run outside Docker (the console in its container gets no host control). `t900-ground-diag` writes one read-only, timestamped report (service status, the last 50 pppd journal lines, `ip addr` of `ppp0`, the device node, `lsusb -d 1a86:7523` with the sysfs location and driver, the last 30 usb/ch341 kernel lines, three pings to the peer, `udevadm info`, the watchdog status); without root (or the `systemd-journal`/`adm` group) it skips the journal parts and names them; `--raspberry` switches to `t900-ppp.service`, `/dev/t900`, peer `10.90.0.1`. `t900-ground-watchdog check` runs from a root `Type=oneshot` service and a 30 s timer: the link is down when `ppp0` is missing, has no IPv4 address or the peer answers none of `PING_COUNT` pings; after `FAIL_AFTER` (180 s) each check may act once, `BACKOFF_BASE` (120 s) after the previous action and doubling to `BACKOFF_MAX` (900 s), in the order restart the PPP service, re-enumerate USB (`usbreset BUS/DEV` of the adapter behind the device node, else unbind/bind `ch341` in sysfs; it refuses to guess between two adapters) and restart, power-cycle (only `POWER_METHOD=uhubctl|relay`: `uhubctl -a off` or the relay "off", `POWER_OFF_SECONDS`, then always "on", also after a failed "off" or a stop request in between) and restart, then again; `MAX_ACTIONS_PER_HOUR` (4) actions in the last hour lead to a "remote unreachable" hold until a new PPP session (an address on a new ifindex) or a reply; a new boot (another kernel `boot_id`) clears the outage and the hold, so `FAIL_AFTER` applies again, while the actions of the last hour still count (a stamp later than the clock, after it went back, does not). It leaves a stopped or disabled PPP service alone, shares one `flock` lock with an operator's `usb-reset` (`/var/lib/t900-ground-link/run.lock`, which names the holder; the kernel releases it with the process, so a crash or a reboot leaves no stale lock, actions run with the lock's descriptor closed, and a check that finds it held 10 min or more logs the holder), logs every action with its output with `logger -t t900-ground-watchdog` (to stderr too outside a unit, where `INVOCATION_ID` is unset), keeps its state in `/var/lib/t900-ground-link/state` (`state.dry-run` for `DRY_RUN=1` or `--dry-run`), and reads `/etc/t900-ground-link/link.conf` literally (no shell sourcing; unknown keys, bad values, a symlink or a file writable by others exit 78). `usb-reset` (`t900-ground-usbreset.service`) always runs live: `DRY_RUN=1` in `link.conf` applies to the timer's checks only and only `--dry-run` on its own command line makes it a dry run (it still records into the state the checks read); it fails, so `t900-link` reports an error, when `USB_RESET_METHOD=none` or `usbreset` does not end in `ok` (usbutils' `usbreset` exits 0 after `can't open [...]` or `failed [...]`). `t900-ground-diag -o DIR` needs DIR to exist (the incident procedure starts with `mkdir -p ~/t900`) and stops before any probe otherwise. `t900-link` is the operator command (`status`, `restart`, `usb-reset`, `diag`, `log`); the polkit rule lets one user (`--user`, default `rdf`) restart the PPP service and start `t900-ground-usbreset.service` without a password (polkit 0.106+). `install.sh` (`--dry-run`, `--user`, `--prefix`, `--watchdog-dry-run|--watchdog-live`, `--no-watchdog`, `--no-polkit`, `--root` for tests) sets `umask 022`, writes only its own files, refuses to replace a file without its marker and a `--prefix` whose `bin`, `sbin` or share directory or any directory above them is not owned by root or is writable by another user (a sticky `/tmp` aside; root's timer runs `sbin/t900-ground-watchdog`), checks the real paths in `--dry-run` too (exit 1 when the install would stop), keeps `link.conf`, and never touches the PPP unit, `/etc/ppp`, udev or a firewall; `uninstall.sh [--purge]`. The console tarball ships the directory (`GROUND_LINK_FILES` in `make_release.py`); the app tree and the image do not. `tools/test_ground_link.py` runs every script against fakes on a PATH with only allowlisted real tools, a fake sysfs and `T900_LINK_NOW`/`T900_LINK_STATE_DIR`/`T900_LINK_CONFIG`/`T900_LINK_SYSFS`/`T900_LINK_PROC`/`T900_LINK_ROOT_UID` (tests only; the installer reads `T900_LINK_ROOT_UID` too). A console button is only a proposal in `packaging/ground-link/README.md`.

## Data contract notes that span several files

- `TelemetrySnapshot` (`frontend/src/types.ts`) mirrors what `tools/sdr_doa_collector.py` produces via `/api/snapshot`, or what `tools/telemetry_source.py` builds from MQTT in the same shape (one DoA view, `doa_candidates.mqtt`, no `csv` or `xml`; its `mqtt` block holds the UNVERIFIED and diagnostic values, `data_out_light` the light read). Every answer has `source` (`kind` `mqtt`, `data_out` or `none`, `reason`, `reasons`); the browser picks the DoA view with `sourceViewNames()`/`primaryCandidate()` (`lib/telemetry.ts`), the badge, the light read's status and doa.xml (the station position over MQTT) with `lib/telemetrySource.ts`. Key fields are `doa_candidates.csv` / `doa_candidates.xml` (kept separate, never silently merged), `native_consistency` (with `frame_relation` and `angle_checked`), `authority`, `publication_gate` (`state` + `reasons` + `checks`), `overall_state`, `node_progress`, `signal_quality`, `collection`, and per-path `resources`.
- `/api/snapshot` is one shared Data Out read (`tools/data_out_reader.py`), not one per request: every viewer gets the last collection for `max(1 s, refresh interval)` from when it started reading the node, a page that sends the collection id it shows as `seen` gets a new read 0.25 s before that, `refresh=1` reads again once the last read is 1 s old, and `fresh_settings=1` also reads settings.json, which the collector otherwise reuses for up to 30 s (`SettingsCache`). So a snapshot can be older than its answer: `collection.age_ms` says by how much, `collection.id`/`collected_at_ms`/`shared` name the read, `collection.refresh_seconds` and `collection.console_base_url` are the saved interval and the console's Data Out URL at the time of the answer, and `settings.read_at_ms`, `settings.reused` and `collection.settings_age_ms` say how old its settings are. The browser ages data from the node read (`lib/snapshotRead.ts`), never from the answer's arrival (the Dashboard HUD age adds `collection.age_ms`), schedules every automatic read, the first one included, from the last answer's node read, and re-reads `/api/console-config` when an answer reports another interval or Data Out URL (another page saved it), or the console refuses the page's URL with `DATA_OUT_URL_NOT_ALLOWED` (another page dropped its host from the list): once per shared read or refusal run (`configResyncFor()`, `refusalResyncFor()` in `App.tsx`), applied like its own save when the URL or interval differs, so no page keeps a second read of an old target or stays refused until a reload. The legacy UI (`--legacy-ui`) sends `refresh=1` from Refresh and Apply & refresh, `seen` on every read, adds the served age to its DoA age, its auto-refresh follows the reported interval (its interval select is saved with Apply), and it follows `console_base_url` (`followConsoleUrl()`, also after a refusal, from `/api/console-config`); and Kontrol's read-back takes settings only from a read at or after the command's `issued_ms`. `DataOutReader.read_reason()` is the one place that decides whether Data Out is read.
- MQTT first (#8; `tools/telemetry_source.py`, `docs/MQTT_KONTRAK.md` section 8): MQTT is fresh when the RDF Node store has a `state` session and a `telemetry/health` of it at most 8 s old with `daq=1` (`HEALTH_FRESH_MS`; the store already refuses health whose `q` does not advance and drops it with a new `sid`). Then every `/api/snapshot` answer is built from `MqttMonitor.rdf_node_view()` and no full collection runs; only the light read (`collect_light()`: status.json, settings.json, doa.xml) runs in a background thread, first at once, then at most every 30 s (`LIGHT_READ_INTERVAL_S`), at once on a new `sid` or `state.cfg` (at most once a second, "light-config", which reads settings.json instead of reusing it) and for `fresh_settings` (Cek ulang, which waits for it); `refresh=1` reads nothing. When MQTT is not fresh the request reads Data Out fully, as before. θ₀ comes from DoA `a` only when this session's `capabilities.angle` is `theta_mirror` (`a`) or `csv_native` (`360 − a`), and from Angular `raw_doa_deg` always as `360 − raw` (DOA_value.html column 1); the vector is Angular `values` (columns 17 onwards, the collector's `angular_power_db`) only from a `flags=63` frame with the DoA's frequency and revision; the same `q` means one record, so two θ₀ more than 1° apart are a `CONFLICT`. The edge sends DoA more often than Angular (`balanced`: 1 s and 4 s), so a frame of an older `q` (`SAME_CONFIG`) gives the vector only while its peak is within 3° of the DoA's θ₀, adding `NATIVE_ANGLE_UNCHECKED`; further away it is `PEAK_MOVED` and the DoA has no vector until the next frame, so the bearing and the curve never point apart. Everything of the light read (settings, `gps_status`, position, ADC and SNR) counts for 65 s (`LIGHT_VALUES_MAX_AGE_MS`) and answers as not read once older (`data_out_light.expired`); `collect_light()` reads settings.json after all when doa.xml shows another frequency or station than with its cached copy. `ok=0`, Angular flags other than 63 and both diagnostic topics never fill a candidate: DOA reads `UNVERIFIED` and shows nothing, and DoA Diagnostics (MQTT DoA card) and Message Monitor show them. The answer keeps authority none, clock `remote_unverified`, gate `BLOCKED` and never `LIVE`; `collection.age_ms` is 0 and each answer has a new `collection.id`. The legacy UI asks `source=data_out` (`DATA_OUT_REQUESTED`), because it renders only the CSV and XML views; the LAN view ignores that flag. New source or `MQTT_*` gate codes need EN and ID labels (`source.reason.*`, the gate dictionaries in `lib/i18n.ts`; `tools/test_telemetry_source.py` checks), and `tools/fixtures/telemetry-source/` is rewritten by `write_source_fixtures()`; the Python suite compares it with what the server builds and Vitest reads it.
- `canonical_angle_deg` is the native θ₀: an array-frame angle, counter-clockwise. It is not a geographic bearing and not necessarily the plotted display peak. Convert with `geographicBearingForBin()` in `lib/polar.ts`.
- `angular_power_db` is a 360-bin angular DoA spectrum, not a frequency spectrum. Its peak bin should equal θ₀ within 3° (`ANGULAR_PEAK_ANGLE_MISMATCH` otherwise).
- Compass/Polar conversion happens in the renderer (`lib/polar.ts`) from settings. Never rewrite source data for display.
- Local freshness expiry must not reset data age on every response. Expired data is cleared or marked stale in active visuals. Show DoA only through `overviewDoaStatus().shown`.
- Health available, Data Out available, native records present, and delivery READY are four different states.
- The RDF Node MQTT contract is `docs/MQTT_KONTRAK.md` (edge commit `8691ad0`; later fields optional), applied by `tools/rdf_node_mqtt_v2.py` and served by `/api/mqtt/rdf-node` as `topics` (the status of each topic's latest message) and `node` (accepted values only). Its `LIVE` is the edge's own gate (DoA `ok=1` or Angular `flags=63`, fresh health with `daq=1` and an advancing `q`, source inside its window) and differs from the collector's `overall_state` `LIVE`, which the console never reaches. `UNVERIFIED` there means the edge's trust-only, RAW or diagnostic data, kept apart from LIVE. Kontrol reads the node session, health and `settings/reported` from it (`rdf_node_control_view()` on the monitor); the Dashboard does not read it yet; `rev` and `revision` are metadata, never an equality gate for LIVE, and the angular `values` and the `settings/reported` text never go through the topic entries.
- `ground_console.py` always collects with `authority="none"` and `clock_source="remote_unverified"`, and nothing passes `canonical_angle_ready=True`. Healthy data therefore reads `overall_state` `UNVERIFIED` (never `LIVE`) and `publication_gate` `BLOCKED` with `DOA_AUTHORITY_NOT_SELECTED`, `CANONICAL_ANGLE_NOT_CONFIGURED` and `GROUND_CLOCK_UNVERIFIED`. That is the console's observation boundary (Kontrol does not change it), not a defect.
- Kontrol sends RDF Node commands in the edge's format (`docs/MQTT_KONTRAK.md` section 9, `tools/rdf_node_commands.py`): `config.patch` on `sdr/v2/uav-01/cmd/config/patch` and `config.get` on `cmd/config/get`, QoS 1, never retained, 15 s TTL, envelope `{v: 2, id, sid, boot, issued_ms, expires_ms, base_rev, op, changes}` built on the server from the latest `state`. The fields are the edge's (`center_frequency_hz`, `gain_db`, `vfo0_frequency_hz`, `vfo0_bandwidth_hz`, `vfo0_squelch_db`); a centre change carries `vfo0_frequency_hz` at the same frequency, and the gain is one of the edge's gain table. A patch needs fresh node health and `base_rev` = `state.cfg`; a `config.get` only a connected monitor and the node session. Kontrol has two layers of state. In the browser: admin `checking`/`locked`/`unlocked`, then `edit` → `review` → `sending` → `done`. On the server, per command: `published` → `delivered` (PUBACK < 128) → `acknowledged` (ACK `ACCEPTED`/`APPLYING`/`VERIFYING`) → final `acked` (the edge's final ACK: `APPLIED`, `PERSISTED_UNVERIFIED`, `OUTCOME_UNKNOWN`, `REJECTED`, `CONFLICT`, `EXPIRED`, `FAILED` or `CANCELLED`, with `result.error`), or final `publish_failed` (publish error or PUBACK ≥ 128), `no_ack` (no ACK by `expires_ms` + 5 s, so about 20 s) or `no_final_ack` (a progress ACK but no final one within 90 s); a `config.get` ends `reported` when its `settings/reported` came, or `no_report` after 60 s. A late final ACK upgrades a timeout state. `monitor_restarted` marks a command whose monitor was replaced. A monitor follows only the ids it published or adopted, so before a Reconnect or an MQTT settings save swaps monitors the server hands every command that is not final to the new one (`ConfigCommandTracker.hand_over()` → `MqttMonitor.adopt_rdf_node_commands()`, before its `start()` and again at the swap under the command lock): the edge's ACKs and a `config.get`'s `settings/reported` then reach the new client, which keeps the settings request through its first `state` of the command's `sid`; the PUBACK stays with the stopped publisher, which the tracker still reads until the command is final. Nothing is resent automatically.
- `APPLIED` is the only success: the edge wrote `settings.json` and saw fresh runtime evidence for each field (`proof`: `FRESH_DAQ_RF_CENTER`, `FRESH_DOA_FREQUENCY`, `FRESH_DAQ_GAIN`). `PERSISTED_UNVERIFIED` (written, evidence incomplete after its verify window, reason `NATIVE_RUNTIME_EVIDENCE_INCOMPLETE`), `OUTCOME_UNKNOWN` and `no_final_ack` are neither success nor failure (Kontrol shows them in an info tone and says to read the settings before sending again). `REJECTED CONFIG_REVISION_CONFLICT` means the node's settings changed after `base_rev` was read: read the values again, review, send. `base_rev` is the node's `state.cfg`, chosen by the server; the browser must echo the revision it reviewed (`CONFIG_REVISION_STALE` otherwise, with nothing sent). Kontrol's current values come from the node's `settings/reported` (only a report whose `rev` is `state.cfg`; the edge sends it after a `config.get`, and only over a TLS link to the broker), then from fresh Data Out `settings.fields` (the collector keeps `vfo_freq_0`, `vfo_bw_0`, `vfo_squelch_0`), otherwise "tidak dilaporkan"; the panel shows which ("Nilai: settings/reported", "Nilai: Data Out (cadangan)"). After a final command, `lib/configVerify.ts` compares the sent values with a `settings/reported` received after the command was issued first, then with Data Out, to show whether the node really changed. The spectrum dock's node frequency comes from the snapshot: `settings.fields.center_freq` in MHz (over MQTT from the light Data Out read) and the DoA view's `frequency_hz_normalized` (the CSV view, or the LIVE MQTT DoA's `f`), not from Kontrol's MQTT values; its "Kirim ke RDF-SDR" drafts the listen VFO as both `center_frequency_hz` and `vfo0_frequency_hz`.

## Known failure modes

- MQTT monitor shows ERROR "MQTT monitor dependency paho-mqtt is not installed": the console starts without paho, but monitoring needs `paho-mqtt==2.1.0` in `.venv`.
- Receiver page says "Receiver is not built": `npm run build` deleted `frontend/dist/receiver`. Run the Receiver builder (or `npm run build:all`).
- System Health shows `/settings.json` as `REUSED` with an age, or a node card value lags a change made on the node: the console reuses settings.json for up to 30 s unless status.json or the DoA views show the settings changed. Kontrol's "Cek ulang" (and a Kontrol command that becomes final) reads it at once; a console restart starts without a copy. Refresh (R) within 1 s of the last read, or a second open page, gets the same shared read, not a new one.
- Basemap missing: MapLibre is only the renderer, and the browser gets every tile from the console's `/api/tiles/<source>/<z>/<x>/<y>` (the page CSP lists no tile host, on purpose). Look at the console log first: `tiles <source>: upstream unavailable (<reason>)` names DNS, refused, timeout, HTTP status, a refused content type or a redirect. Then check HTTPS from the console host (not the browser) to the hosts in `TILE_SOURCES` (`tools/tile_cache.py`), the environment proxy (`HTTPS_PROXY`/`NO_PROXY`), and that `--tile-cache-dir` is writable (`tile cache ... is not writable` in the log; tiles are then served but not kept). `curl -s -D - -o /dev/null http://127.0.0.1:8787/api/tiles/osm/0/0/0` shows `X-Tile-Cache: hit|miss|stale`; 504 means not cached and the upstream unreachable (a failing host backs off 30 s). A tile failure does not mean the overlay failed; the map shows BASEMAP UNAVAILABLE · <style> when tiles of that style fail and none has drawn since the style was chosen or last retried, and BASEMAP PARTIAL · <style> when they keep failing (4 within 15 s, `BASEMAP_PARTIAL_WINDOW_MS` in `lib/map.ts`) while others draw, as offline with part of the view cached. Both retry every 60 s (MapLibre does not ask for a failed tile again by itself); a partial retry that brings no failure within 15 s clears the chip, one that loads nothing turns it UNAVAILABLE, and so does a view that draws none of the style's tiles any more (checked every 5 s, as after panning offline to an area never viewed). The map never switches style by itself. Offline, only areas and styles viewed before are cached (no bulk prefetch, by the providers' policies). Light and Dark share the Standard (`osm`) tiles.
- Overlay in the DOM but invisible: check `doaReady` (DAQ, ADC overdrive, CONFLICT, missing view, stalled node), coordinate validity and camera, a fresh 360-length `angular_power_db`, non-empty geometry, visibility/opacity/paint, canvas fallback stacking and transform, map resize, and stale `localStorage` overlay settings.
- Plot or map resets on data update: data updates must go through the restyle/set-data path. Do not resend layout/camera. Keep user state (zoom, rotation, head-up, manual range) separate from the data revision.
- Data STALE with `NODE_CLOCK_STALLED` while port 8081 still answers: the node's DSP stopped. This is reported, not a console bug.
- The Source chip shows `Data Out (fallback)`/`Data Out (cadangan)` although Message Monitor shows MQTT connected: MQTT is not fresh, and the chip's tooltip and `source.reason` in `/api/snapshot` say why. `MQTT_NO_SESSION`: no RDF Node `state` on this broker yet (the edge does not publish, or another broker). `MQTT_NO_HEALTH`/`MQTT_HEALTH_STALE`: no `telemetry/health` of this session in 8 s (the edge stopped, the link dropped, or the store refused it: the RDF Node topic table in Message Monitor names the code, such as a `q` that does not advance). `MQTT_DAQ_NOT_HEALTHY`: health says `daq` 0 or 2, and the Data Out answer shows the DAQ detail. `MQTT_DISABLED`: no MQTT host, no paho, or the monitor stopped. `none`/`tidak ada`: Data Out does not answer either.
- Source `MQTT`, DOA `UNVERIFIED` and no bearing: the RDF-SDR sends only DoA `ok=0` and Angular flags other than 63, which is the edge default while its authority and angle are not verified. By design; the values show in DoA Diagnostics and Message Monitor. DOA `INCOMPLETE` with `MQTT_ANGULAR_UNAVAILABLE`: the stream profile is `control` (no Angular; use `balanced` or `graph_u8`) or the Angular frame is of another frequency or revision, or of an older record whose peak is more than 3° from the newer DoA (`angular_pairing` `PEAK_MOVED`, until the next frame); with `MQTT_ANGLE_CONVENTION_UNKNOWN`: no `capabilities` of this session yet.
- Source `MQTT` with Data Out down: the bearing stays, while the node card has no centre frequency or gain, the compass offset keeps its last Data Out value (at most 90 s, then it is assumed) and the map its last position until a light read succeeds (every 30 s).
- Old UI after `git pull` (rail instead of the top bar, no dashboard): `frontend/dist` is stale. Run `cd frontend && npm ci && npm run build:all`, then restart the console (the Python side changed too).
- Kontrol shows "No ACK yet" (`no_ack`) about 20 s after Send: the RDF Node edge did not answer on `sdr/v2/uav-01/ack/config`. Either its agent is not running, it uses another broker, or the command went to a broker the edge does not read.
- Kontrol Send stays disabled ("Send needs ..."), or POST returns 409 `NODE_SESSION_UNAVAILABLE`, `NODE_NOT_FRESH` or `CONFIG_REVISION_UNKNOWN`: no RDF Node `state` has arrived since the monitor connected, `telemetry/health` is older than 8 s, or the `state` carries `cfg: null` (the edge has no settings revision yet). Message Monitor's RDF Node view shows which. A config patch needs a live node; a `config.get` does not need fresh health.
- Kontrol shows `REJECTED · TLS_REQUIRED_FOR_SETTINGS_REPORT` after "Baca settings", and the values say "Data Out (cadangan)": the edge sends `settings/reported` only when its own connection to the broker uses TLS. Give the broker a TLS listener for the RDF-SDR (the console itself stays on the plain loopback listener) and point the edge at it; until then the values come from Data Out. Patches still work.
- Kontrol shows `REJECTED · CONFIG_REVISION_CONFLICT` (or the POST answers 409 `CONFIG_REVISION_STALE`): the node's settings changed after the values were read, often by `rdf-ground.service`, another console or the node's own panel. Read the values again, review, send. `REJECTED · BUSY` (or `SETTINGS_REQUEST_PENDING`, `REQUEST_RATE_LIMIT`): the edge is working on another command, possibly from `rdf-ground.service`. Run one controller at a time: one console with Kontrol open, or `rdf-ground.service`.
- Kontrol shows `REJECTED · EXPIRED_OR_INVALID_DEADLINE`: the command reached the edge after its 15 s lifetime, or the console host's clock is more than 1 s ahead of the RDF-SDR's (`issued_ms` comes from the console server's clock). Check NTP on both. `CLOCK_UNTRUSTED`: the RDF-SDR clock is not synchronized, so it takes no changes.
- Kontrol shows `PERSISTED_UNVERIFIED` or `OUTCOME_UNKNOWN`: not a failure and not a success. Do not send the same change again; press "Baca settings" (or wait for the read-back) and compare. `FAILED · CONFIG_TARGET_NOT_READY` or the panel line "remote_config_patch false": the edge has no approved settings target (`sudo rdf-node controls approve --settings` on the RDF-SDR).
- The console's MQTT client has no TLS or credentials: it needs a broker listener that admits it anonymously and without TLS (on the groundstation, the loopback listener). Use `tools/mqtt_stage4.conf` (anonymous, `127.0.0.1:18884`) locally.
- `publish_failed` with a PUBACK reason ≥ 128 (135 is "Not authorized"): the broker ACL does not let the console's anonymous client publish to `sdr/v2/uav-01/cmd/config/patch` (and `cmd/config/get`).
- Message Monitor's RDF Node view shows every telemetry topic `IGNORED NO_SESSION`: no `state` has arrived since the monitor connected (the edge publishes it retained and at least every 60 s; a retained clear of `state` also ends the session). `INCONSISTENT SESSION_MISMATCH`: the messages carry another `sid` than the last `state`, typically for a moment after the edge agent restarted.
- RDF Node telemetry `STALE SOURCE_TIMESTAMP_NOT_FRESH` (or `SOURCE_TIME_FUTURE`) on every message, so DoA and Angular never become `LIVE`: the Raspberry and groundstation clocks differ by more than the window (health 8 s, DoA 5 s, Angular 10 s, 1 s ahead). Sync both clocks; the console never replaces a source time with its receipt time.
- RDF Node `telemetry/doa` and `telemetry/angular` show `UNVERIFIED`, never `LIVE`: the edge runs with `authority_verified`/`angle_verified` off (its default), so it sends DoA `ok=0` with the RAW angle and Angular with flags 23. That is the contract, not a parser fault; v2.0.0 reported the RAW angle above 180° as `INVALID_FIELD` because it allowed only −180..180.
- RDF Node `settings/reported` shows `IGNORED UNREQUESTED_SETTINGS_REPORT`: another Ground on the broker (such as `rdf-ground.service`) sent the `config.get`; the console accepts only answers to its own registered requests.
- Saving the Data Out URL shows "Use http://<host>:8081 with a host from the list: …" (`DATA_OUT_URL_NOT_ALLOWED`), or the console exits with `--base-url: the Data Out URL must be http://HOST:8081 with HOST in the Data Out host list (…)`: the host is not in `data_out_hosts`. Add it in Configuration → Connection & refresh (Data Out (fallback) hosts) and save it with the URL; before a first start, `SDR_DOA_SEED_DATA_OUT_HOSTS` or `install.sh --data-out-hosts`. The port is always 8081.
- Data Out `doasdr.local could not be resolved (system and mDNS); use an IP address` (System Health: "… also not over mDNS"): neither the system resolver nor the console's one-shot mDNS query found the name, typically in Docker (no nss-mdns in the image) with the node off, on another segment, or multicast blocked, or a host firewall dropped the answer (the node answers by unicast from UDP port 5353 to the query's ephemeral port, which a stateful firewall does not take for a reply; with ufw, `sudo ufw allow proto udp from <LAN subnet> port 5353`); through an HTTP proxy there is no mDNS fallback at all (set `NO_PROXY`). Put the node's IP in the URL (and the host list). The plain `host name resolution failed` means a non-`.local` name, or a console started without the resolver. When the fallback works, System Health's Data Out card shows `mDNS <address>` and `collection.host_resolution.method` is `mdns`.
- Settings look unsaved after a restart: the console was started with `--base-url` or `--mqtt-*`, which override `console.json` for that run. Remove them from the unit or command; change settings in Konfigurasi.
- Container exits with 73 "not writable by uid 10001": a bind mount for `/data` is owned by another user. Use the named volume or `chown 10001:10001` the directory.
- `docker compose build` from a git worktree stops in `check-build-context.sh`: the Receiver builder needs `.git/modules/vendor/BrowSDR`. Build from a regular clone or from the release with `Dockerfile.release`.
- Records ZIP download answers 503 `ARCHIVE_EXPORT_BUSY`: two ZIPs are already streaming (selection and single-scan ZIPs share two slots). Wait for one to finish; a prepared export stays valid for its 120 s.
- A Records download paused or stalled for over 60 s fails (the write timeout frees its slot). A one-time ZIP export cannot be resumed: prepare it again. Single-file downloads restart from the beginning (no Range on download routes).
- Records shows "Open the Receiver from this console." (403 `ORIGIN_REJECTED` on GET): the console was reached through a port-forward or proxy that changes the Host or port (for example `ssh -L 9000:127.0.0.1:8787`), or another site asked for Receiver data. Open the console on its own loopback address and port.
- LAN access stays `CLOSED` although it is enabled: the reason is in the Configuration card, `/api/health` `lan_access.reason` and the log. `ADMIN_PASSWORD_DEFAULT`/`ADMIN_DISABLED`: set `SDR_DOA_ADMIN_PASSWORD` and restart. `BIND_FAILED` with `EADDRINUSE`: something else holds the port, often the old `socat 0.0.0.0:8788` forward the LAN view replaces; `EADDRNOTAVAIL`: the bind address is not one of this host's (yet). The console tries both again (5, 10, 20, 40 s, then every 60 s, `LAN_BIND_RETRY_DELAYS_S`) while the setting stays enabled, so a LAN address that comes up after a boot start opens the view by itself; the log names the first failure and `after a failed bind` when it opens. Any other errno stays closed until a save or a restart.
- A tablet gets 403 with an empty body from the LAN view: its address is not in `allowed_clients` (the log names it once a minute). 503 with an empty body: 32 LAN requests were open at once (`LAN view busy` in the log, once a minute); it answers again when they end. 403 `ORIGIN_REJECTED`: it used a Host that is not an IP, this host's name or `<host name>.local` (a DNS name, a proxy, or a `.local` name avahi renamed after a conflict, such as `<host name>-2.local`). 403/405 `LAN_READ_ONLY`: a write or a route the LAN view never answers (Receiver, Records, Kontrol, admin).
- The LAN view's Spektrum dock or Receiver route shows SOURCE LOST/SUMBER PUTUS: nothing posted to `/api/mirror/receiver` for 10 s. On the groundstation the console page must have the Receiver frame mounted (open the Receiver once, or Mulai in the dock) and stay open; a page loaded before the LAN view was enabled starts posting within 10 s (its `/api/health` check); a tab hidden for minutes can lose its heartbeat. `curl -s --noproxy '*' http://127.0.0.1:8787/api/mirror/receiver` on the groundstation shows `source_age_ms`. STALE with RX running: the groundstation page is hidden (frames flow only while it is visible) or the radio stopped delivering frames.
- Retention removed records but `receiver.sqlite3` keeps its size: SQLite reuses the freed pages and the console never runs VACUUM; only audio files give disk space back at once.
- On a full disk a large scan delete can fail, because SQLite needs journal space for each batch: delete audio first (its files free space at once), then the scan.
- `sdr-doa-docker install` or `update` fails at the pull with `denied` or `unauthorized`: the GHCR package is still private (set it Public once, see "CI and releases"), or Docker holds an expired `ghcr.io` login (`docker logout ghcr.io`; public images need none).
- `sdr-doa-docker update` exits 1 and the old image runs again: the new one did not report healthy in time. `DIR/update.log` has the reason on its `FAILED` line and `DIR/.bad-images` the image, which `update --auto` skips until another is published. The native updater does the same with the release (`sdr-doa-console auto-update status`, `update-state.json`); `update --to X.Y.Z` retries it.
- Native console not running after a reboot: lingering is off (`loginctl show-user $USER -p Linger`); run `sudo loginctl enable-linger $USER`.
- Docker or native auto-update logs `deferred: Receiver recording or scan active` every night: `/api/health` reports `receiver_busy` (a recording or scan archive is running, or a session was written within 120 s). It updates by itself after 7 days of deferrals; `sudo sdr-doa-docker update --yes` or `sdr-doa-console update --yes` updates now.
- `sdr-doa-docker auto-update on` refuses with "not owned by root or is writable by another user": root's timer only runs a root-only copy of the script for a root-only DIR. Install in `/opt` as root, or use the printed crontab line as the DIR's owner. "cannot read DIR/.env (mode 0600); run with sudo": the install is root's.
- `sdr-doa-docker` 3 refuses a directory with "holds the RDF-SDR agent install of sdr-doa-docker 2": that is an agent install of version 2, which the console no longer manages (the Raspberry runs the RDF Node edge). Stop it with `docker compose down` in that directory; to put the console there, then move its `compose.yml` away and run `install` (`--force` does not replace it). `--agent` and its options are refused the same way.
- PPP to the RDF-SDR stays down (`LCP: timeout` in `journalctl -u t900-ground-ppp`, Data Out unreachable, no MQTT from the edge): not a console fault. Run `sudo t900-ground-diag` and `t900-link status`; "remote unreachable" means the watchdog's actions of the last hour did not help. The incident procedure (restart, then `usbreset` and restart, then unplug and replug, 30–60 s and a diag after each) and what each outcome says about the layer are in `packaging/ground-link/README.md`. `t900-ground-watchdog` exits 78 on a `link.conf` error (`sudo t900-ground-watchdog check-config`).
